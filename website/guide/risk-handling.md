# 风险与处置

## 本机风险统计

在聊天里说 **“打开风险统计”**。0.3.10 的本机风险页可选择 **全部编辑器 / Codex / Cursor**，并按项目、处置状态或关键词筛选；统计卡片与项目分布随筛选变化。

读取的是当前操作系统用户数据目录中已保存的两类编辑器记录，不是当前聊天临时结果，也不是所有电脑或所有用户的数据。页面区分已确认待处理、待确认候选、暂缓、排除和复查解决；原始扫描命中数不等于有效漏洞数。

跨编辑器记录保留各自来源和处置。同一个问题若分别在两边保存，汇总时可能出现两条，当前不做跨编辑器合并去重。读取上限、损坏或不可访问数据会提示缺口；“0 条”不能单独证明项目安全。

页面只读，不扫描、不修改处置，也不启动消耗监控。历史记录不证明当前磁盘版本。

## 先读懂问题

一条可用的风险说明至少包含：具体位置与问题、能够触发的前提、可能影响、已有防护、建议修复以及尚未确认的范围。严重程度标签不能代替这些事实。

0.3.10 会区分扫描器的待核实提示与已结合代码复核的风险。检查工具缺失、数据过期或覆盖不完整属于检查状态，不是漏洞发现，不应据此生成修复选择。回复随当前对话语言表达，无需照抄固定模板。

## 三种处置不是同一件事

| 选择 | 表示什么 | 不表示什么 |
| --- | --- | --- |
| 修复 | 授权处理明确问题与范围 | 不授权顺手改造其他模块 |
| 稍后处理 | 本轮不修，保留风险与记录 | 不等于风险消失 |
| 排除 | 记录明确的误报或不再提醒决定及依据 | 不自动证明代码无风险 |

用户决定与 AI 技术评估分别记录。不要为了得到绿色结果而排除一个未核实的问题。

同一问题与范围已经获得明确修复授权时，助手会继续处理，不要求重复选择；“先不改代码”本身不等于已经保存“排除”或“稍后处理”的处置。已保存的稍后处理或排除项不应在每次查询时重复提醒。

## 只问影响时

可以说“先分析修复这项风险会影响哪些接口、调用方和测试，不改代码”。这一步应保持只读，说明证据与未知；若仍有阻碍执行的未知，应保留它们，而不是猜测后动手。

## 修复后

让 Agent 沿原风险复查，确认原触发条件与修复防护，而不只是再跑一次普通测试。结果可能是已修复、仍存在或尚不能确定；复查证据不足时应明确说明。

历史记录查询不会重新索取处置选择。涉及真实密钥时，应按你的应急流程轮换凭据，不能仅以删除代码作为泄露已经消除的证明。
