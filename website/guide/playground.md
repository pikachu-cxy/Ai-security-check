# 动手测试用例

用这些小用例确认你自己的接入是否按预期工作。沿用 [Demo](./demo.md) 中的独立 Git 文件夹；每个用例都给出操作与观察点，不要求固定告警数量。

## 用例 1：确认连接，不改代码

在新聊天中发送：

```text
请只查询 AI Security Runtime 的连接、版本和检查组件状态。
不要扫描或修改项目。
```

**预期**：返回实际连接和准备状态；不因状态查询而发起项目扫描。没有调用成功或组件仍未就绪时，先按[安装验证](./verify.md)处理。

## 用例 2：检查一个已知问题

将 `demo.py` 保存为 Demo 中的 `os.system` 版本，然后发送：

```text
请使用 AI Security Runtime 静态检查 demo.py，分析 name 到命令执行的路径。
不修改文件、不执行示例，说明实际检查范围与触发条件。
```

**预期**：在组件和规则可用时，应识别命令拼接线索，并解释“外部输入可控”这一前提。可以记录文件行号、实际规则、是否完成与未确认项，避免只保存一句“检测到了”。

**没有发现时**：先确认服务实际执行、Python 规则启用、文件已保存且纳入范围。若检查完成仍未识别，记录为待调查结果，不自行当作通过。

## 用例 3：对照安全写法

按 Demo 的明确修复请求，让助手把原函数改为校验文件名、使用参数列表的版本，并沿原问题复查。

**预期**：说明原命令拼接路径如何消除，复查对应同一问题。其他发现和未覆盖范围单独保留；“零发现”本身不足以证明原问题已修复。

## 用例 4：只分析修复影响

在新的独立示例文件中放入 Demo 的原始写法，发起检查后回复：

```text
先分析修复刚才这项命令拼接问题会影响什么，不改代码。
```

**预期**：得到影响说明，文件保持原样。之后想修复时，再明确说“修复这项问题”；如果选择稍后处理，则保留风险记录。

## 用例 5：完整接入后的开发任务检查

适用于已完成连接验证的 Codex 或 Cursor 完整接入。如果已经完成对应编辑器页的 `labels.py` 小任务，可直接记录那次结果，无需重复创建文件。否则，在示例项目的新聊天中发送：

```text
请新建 labels.py，实现 normalize_label(text)，去除首尾空格并转为小写。
完成后检查这次改动，告诉我实际覆盖和未完成项。无需安装依赖。
```

**预期**：正常完成开发需求，并对本次真实改动给出检查状态。有明确覆盖缺口时应保留原因；不能用“文件已创建”代替检查结果。手动 MCP 接入没有自动任务编排，不以此用例判断自动接入成功。

功能上还可以对照下面的输入输出。已有可用的 Python 环境时，可让助手运行这些普通函数用例；没有实际运行就记录“未运行”，不要把代码阅读当成测试通过。

| 输入 | `normalize_label` 预期返回 |
| --- | --- |
| `"  Hello  "` | `"hello"` |
| `"  MiXeD Case  "` | `"mixed case"` |
| `"   "` | `""` |

功能用例验证函数行为；安全检查状态仍需单独记录。本页不要求执行 Demo 中故意保留问题的导出函数。

## 记录你的结果

可以复制下面的清单到个人测试记录中：

| 用例 | 结果（通过 / 未通过 / 未完成） | 实际观察与诊断 |
| --- | --- | --- |
| 1. 连接与状态查询 | 待填写 | 服务调用、版本、组件状态 |
| 2. 已知命令拼接问题 | 待填写 | 文件位置、检查范围、触发条件 |
| 3. 修复与原问题复查 | 待填写 | 原风险记录、修复依据、剩余未知 |
| 4. 只分析影响 | 待填写 | 文件是否保持原样 |
| 5. 开发任务检查（适用时） | 待填写 | 实际改动与检查完成情况 |

完成后可直接保留或删除这个独立示例文件夹。不要将故意有问题的样例放入真实项目。反馈问题时附上脱敏记录、系统和编辑器版本即可。

## 用例 6：重连后读取原检查

保存用例 5 的检查引用。在原聊天恢复 MCP 连接后，请助手只读该检查和风险处置，不新建、不修改、不重扫。预期原范围、扫描版本和处置仍可读取；凭证缺失时报告接入问题，不猜测身份。

## 用例 7：按编辑器查看风险

说“打开风险统计”，依次选择全部编辑器、Codex、Cursor，核对来源列、筛选统计与读取状态。只读历史记录即可，不必为了制造数据重复扫描。零记录和读取失败分别判断。
