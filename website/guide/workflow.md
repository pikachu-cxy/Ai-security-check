# 日常怎么用

接入并[确认安装成功](./verify.md)后，直接在项目聊天里提出开发需求。完整接入会把本次改动的检查结果带回任务总结；手动 MCP 接入需要你主动提出检查请求。

## 让 AI 完成需求并检查改动

描述你想要的结果和需要保持的行为。例如：

```text
给文件导出功能增加文件名校验，保持返回格式和现有权限判断。
完成后检查这次改动，说明发现的问题、实际检查范围和未完成项。
```

你不需要先提交 Git，也不需要自己输入检查工具名。助手应在编辑前保留真实工作区状态，完成开发后检查实际改动和必要的关联代码。

0.3.7 会在必需源码窗口尚未读完或复核单元尚未提交时要求 Agent 继续，避免只登记文件就提前结束。Git 拉取和日常开发产生的改动使用同一套范围核对；拉取源码不会自动更新已安装产品。

## 检查已有项目

想了解已有代码的问题，可以明确指定范围：

```text
请检查当前项目的文件上传与下载模块，重点看路径边界和权限判断。
先只检查并解释风险，不修改代码。
```

范围较大时可以分模块处理。检查结果应说明哪些文件和能力实际覆盖，以及哪些部分尚不能确认。

### 0.3.8 的扫描体验改进

以下改进已包含在 0.3.8 发行包中；使用旧版本的用户需安装新包并重新连接宿主。

- 可以明确说“只检查 `demo.py`，不要扩大到其他源码”。文件范围检查会分别说明请求文件、实际目标、辅助配置/依赖上下文和排除项。
- 再次检查整个项目时，会核验源码内容与文件清单、规则、引擎、配置、数据库有效性及此前执行是否完整。证据仍有效才复用，并说明结果来自何时；缺证或变化则重新扫描。
- 明确说“重新扫描，不复用旧结果”会强制执行新扫描。查看历史结果、继续复核已有问题不会因此自动重扫。
- 支持 MCP 进度通知的宿主可显示准备、核验和扫描阶段；不支持时仍返回相同结果和计时。Runtime 计时不包含宿主模型分析、排队或人工确认，未知耗时不会被填成零。

Windows/macOS 和 Codex/Cursor 共用范围、复用及授权逻辑。宿主界面是否实时显示进度分别验收。
复用不会冒充一次新扫描或新的任务完成证明，不会代替需要的代码复核，也不会批准修复。

## 看到风险之后怎么说

| 你想做什么 | 可以这样回复 |
| --- | --- |
| 先了解影响 | “先分析修复这项路径穿越问题会影响哪些接口和调用方，不改代码。” |
| 修复具体问题 | “修复刚才这项路径穿越问题，保留现有权限检查，完成后沿原问题复查。” |
| 这次先不修 | “这项问题稍后处理，请保留记录。” |
| 认为是误报 | “入口已有这些校验，请核实并记录排除依据。” |

每项风险都应给出位置、触发条件、可能影响、已有防护和未知。详情见[理解与处理风险](./risk-handling.md)。

## 如何判断任务完成

开发结果与安全检查应分别说明。正常的任务总结应让你知道：

- 需求改了什么，以及相关验证结果。
- 安全检查覆盖了什么，是否存在未完成范围。
- 有哪些具体问题需要你决定。
- 已批准的修复是否沿原问题完成复查，还有什么不能确认。

如果中途断线，继续原聊天并要求恢复原任务。查询历史结果时无需重新扫描；新任务没有发现问题，也不能代替原问题的修复复查。

### “部分覆盖 / PARTIAL”是什么意思

表示本轮检查还有不能确认的范围，不代表已经发现漏洞。例如源码不可读、原始比较记录缺失、证据中的凭据值被遮盖而影响判断，或实际预算已经耗尽。总结应给出具体原因和未完成范围；仍可继续读取的必需源码不应被直接跳过。

静态检查提交了多少文件，与 Agent 实际复核了多少代码是两项事实。普通测试通过或静态零发现，都不能代替尚未完成的源码复核。
