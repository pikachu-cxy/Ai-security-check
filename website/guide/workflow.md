# 日常怎么用

本页说明 **0.3.9 正式版的当前用法**。接入并[确认安装成功](./verify.md)后，在实际源码根目录的聊天中提出需求。Codex / Cursor 完整接入会把本次改动的检查结果带回任务总结；手动 MCP 接入需要你主动提出检查请求。版本演进见[更新记录](../reference/changelog.md)。

## 每天从哪里开始

打开包含源码和 Git 仓库的项目根目录，避免停留在 ZIP 的外层解压目录。安装或升级后完全退出并重启编辑器，在项目中新建聊天，先完成一次只读连接验证；日常无需反复安装或先执行整项目扫描。

| 你要做什么 | 可以这样说 |
| --- | --- |
| 正常开发 | “完成这个需求，并检查本次改动，说明实际覆盖和未完成项。” |
| 只查现状 | “只查询连接、实际构建、组件和当前项目路径，不扫描、不修改。” |
| 检查已有代码 | “只检查上传模块，解释风险，先不改代码。” |
| 查看已有结果 | “查看上次检查结果和已有处置，不重新扫描。” |
| 明确重扫 | “重新扫描当前项目，不复用旧结果，先不修改代码。” |

安装状态正常但项目显示 `NEEDS_SCAN`，只表示尚无扫描记录；`READY` 表示组件可用，两者都不代表项目已经通过检查。

## 让 AI 完成需求并检查改动

描述你想要的结果和需要保持的行为。例如：

```text
给文件导出功能增加文件名校验，保持返回格式和现有权限判断。
完成后检查这次改动，说明发现的问题、实际检查范围和未完成项。
```

你不需要先提交 Git，也不需要自己输入检查工具名。助手应在编辑前保留真实工作区状态，完成开发后检查实际改动和必要的关联代码。

当前任务核查会要求助手读完必需源码窗口并提交各文件的复核结果，不能只登记文件就提前结束。Git 拉取和日常开发产生的改动使用同一套范围核对；拉取源码不会自动更新已安装产品。普通聊天、只读查询和无改动任务不应额外触发项目扫描。

## 检查已有项目

想了解已有代码的问题，可以明确指定范围：

```text
请检查当前项目的文件上传与下载模块，重点看路径边界和权限判断。
先只检查并解释风险，不修改代码。
```

范围较大时可以分模块处理。检查结果应说明哪些文件和能力实际覆盖，以及哪些部分尚不能确认。

### 文件范围、结果复用与进度

0.3.9 已包含以下能力，按本次需要选择范围即可：

- 可以明确说“只检查 `demo.py`，不要扩大到其他源码”。文件范围检查会分别说明请求文件、实际目标、辅助配置/依赖上下文和排除项。
- 再次检查整个项目时，会核验源码内容与文件清单、规则、引擎、配置、数据库有效性及此前执行是否完整。证据仍有效才复用，并说明结果来自何时；缺证或变化则重新扫描。
- 明确说“重新扫描，不复用旧结果”会强制执行新扫描。查看历史结果、继续复核已有问题不会因此自动重扫。
- 支持 MCP 进度通知的宿主可显示准备、核验和扫描阶段；不支持时仍返回相同结果和计时。Runtime 计时不包含宿主模型分析、排队或人工确认，未知耗时不会被填成零。

Windows/macOS 和 Codex/Cursor 共用范围、复用及授权逻辑，界面是否实时显示进度取决于宿主。复用结果会说明原检查时间，不代替本次需要的代码复核或修复授权。

### 组件未就绪时

0.3.9 会区分检查工具缺失、执行身份无法核验、漏洞库缺失、数据过期与更新时间未知。先按[准备状态](./installation.md#查看准备进度)查看具体组件与原因，处理后重试相同范围；不要仅凭“检查未完成”反复重装或清空缓存。系统 Semgrep 身份无法核验时，在线准备可创建独立受管环境；显式指定的工具路径仍需自行核对。

## 查看上下文开销与 token

0.3.9 在 Codex 当前聊天中支持直接说 **“启动本聊天的消耗监控。”** 页面自动开始观察，结束后点 **结束并导出报告**，保存包含 HTML、JSON 和说明的 ZIP，无需手动找日志。

报告展示本窗口聊天 token、观察时长及已关联工具耗时，不能可靠拆分的纯开发 / 纯安全 token 保持未知。监控不启动模型或扫描，错误、停止或移除监控模块不改变核心产品行为。完整使用与隐私边界见[监测指南](./context-cost.md)。

## 长行代码与检查覆盖

0.3.9 的新任务完整保存脱敏长行，单次响应放不下时自动分片并继续读取，全部字符交付后才满足整行覆盖。仍保留单次响应、源文件与任务存储上限；超过容量或旧前像已截断时明确说明缺口，不因升级补造历史证据。

## 看到风险之后怎么说

| 你想做什么 | 可以这样回复 |
| --- | --- |
| 先了解影响 | “先分析修复这项路径穿越问题会影响哪些接口和调用方，不改代码。” |
| 修复具体问题 | “修复刚才这项路径穿越问题，保留现有权限检查，完成后沿原问题复查。” |
| 这次先不修 | “这项问题稍后处理，请保留记录。” |
| 认为是误报 | “入口已有这些校验，请核实并记录排除依据。” |

扫描器返回的提示会先结合代码核实；尚未确认实际影响的提示应明确标注为待核实。每项风险都应给出位置、触发条件、可能影响、已有防护和未知。已有同一问题与范围的修复授权会继续沿用，无需重复回复固定口令。详情见[理解与处理风险](./risk-handling.md)。

## 如何判断任务完成

开发结果与安全检查应分别说明。正常的任务总结应让你知道：

- 需求改了什么，以及相关验证结果。
- 安全检查覆盖了什么，是否存在未完成范围。
- 有哪些具体问题需要你决定。
- 已批准的修复是否沿原问题完成复查，还有什么不能确认。

如果中途断线，继续原聊天并要求恢复原任务。查询历史结果时无需重新扫描；新任务没有发现问题，也不能代替原问题的修复复查。

### “部分覆盖 / PARTIAL”是什么意思

表示本轮检查还有不能确认的范围，不代表已经发现漏洞。例如源码不可读、原始比较记录缺失、证据中的凭据值被遮盖而影响判断，或实际预算已经耗尽。总结应给出具体原因和未完成范围；仍可继续读取的必需源码不应被直接跳过。

静态检查提交了多少文件，与 Agent 实际复核了多少代码是两项事实。普通测试通过或静态零发现，都不能代替尚未完成的源码复核。
