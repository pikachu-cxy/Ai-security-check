# 安装成功了吗？

依次确认 **编辑器已连接、构建符合预期、检查组件就绪、项目路径正确**，再用独立示例确认实际检查能完成。

## 1. 重启后查询实际状态

安装完成后完全退出并重新打开编辑器。

## 2. 对照结果判断

| 你看到的结果 | 表示什么 | 下一步 |
| --- | --- | --- |
| 工具调用成功，构建符合预期，组件就绪且项目路径正确 | 连接和检查组件可用 | 完成下面的独立 Demo |
| 安装结束，但组件仍在下载 | 程序已接入，检查能力还在准备 | [查看进度](./installation.md#查看准备进度)，等待完成 |
| 有 MCP 条目，但调用失败或找不到工具 | 还未建立可用连接 | 按下方[连接排查](#connection)处理 |
| 版本号相同，但 `build_id` 或来源提交与安装发行不符 | 可能仍连接旧构建或不同安装方式 | 核对[发行与构建记录](../downloads.md#build-details)，确认实际启动程序 |
| 某个组件缺失、启动失败或数据过期 | 对应检查范围暂不可用 | 记录失败组件和具体诊断 |
| 项目绝对路径不符 | 当前连接没有绑定要检查的项目 | 在正确项目中新建聊天，核对配置作用域 |
| `READY` 且项目显示 `NEEDS_SCAN` | 组件可用，该项目尚无扫描记录 | 安装不因此失败；按需要明确发起第一次检查 |

### 项目目录应该选哪一层？

使用包含项目源码和 Git 仓库的实际根目录，不要选 ZIP 外层解压目录。要求助手显式传入该根目录的绝对路径进行只读查询。路径被拒绝时，先核对目录、Git 状态和返回诊断；拒绝码本身不说明具体原因，不要推断需要重装产品。

从源码开发版切换到官网完整包时，确认编辑器实际启动的是受管安装目录中的程序，而不是旧源码目录里的 Python。完整包的默认安装位置为 `%LOCALAPPDATA%\AI-Security-Runtime-install`；版本相同仍需核对 `build_id` 与来源提交。

## 3. 完成一次实际检查

打开[第一个使用 Demo](./demo.md)，使用独立的 `security-runtime-demo` Git 文件夹发起检查。它不要求执行示例函数或安装业务依赖。

**完成标志**：聊天中返回本次检查的实际范围、执行状态，以及具体发现或零发现结果。覆盖缺口应明确说明，不能只用“文件已创建”或“工具已连接”代替检查结果。

## 遇到问题时

### 找不到程序或命令

- Windows / Mac 完整包：确认已完整解压，并在能看到 `security-check` 文件夹的目录执行包内命令。
- Mac 自动安装：终端查询使用 `"$HOME/.local/share/AI-Security-Runtime-macos-trial/security-check"`，无需进入下载目录，也不要假设已加入 PATH。

完整查询示例见[选择程序路径](./installation.md#runtime-path)。Mac 粘贴阶段的系统提醒另见[粘贴提醒排查](../reference/faq.md#macos-paste)。

### 重启后仍未连接 {#connection}

先确认编辑器中的服务已启用，再查看其实际启动错误。版本仍旧时，确认已完全退出旧进程，并核对 `build_id`；使用 Mac 自动安装时请保留产品安装目录，手动 MCP 接入则需要保留配置指向的文件夹。

[本地接入状态命令](./installation.md#查看接入状态)可帮助定位配置问题，但配置正确仍需要编辑器内真实调用确认。

### 准备很久或某个组件失败

首次下载受网络和已有缓存影响。[查看准备进度](./installation.md#查看准备进度)，记录失败组件、状态和诊断。不要用反复清空缓存或覆盖配置代替排查。

### 检查提示未完成

查看结果列出的具体范围和原因。组件未就绪、文件数量或大小超限、不可读路径、严格审计中的改前记录缺失等情况要分别判断；“未完成”不等于发现漏洞，也不能当成检查通过。

仍需帮助时，使用[反馈模板](../reference/faq.md#report)。

::: details 高级：核对构建和任务能力
让助手读取已连接服务的 `get_runtime_info`，核对 `build_id`、来源提交与配套 Skill。默认开发需要记录编辑、收尾和读取结果的轻量检查能力；只有显式严格审计或原有严格任务才使用 `task-review-plan-v3`。缺少能力时更新配置实际指向的 Runtime 并重连，不能只替换 Skill。
