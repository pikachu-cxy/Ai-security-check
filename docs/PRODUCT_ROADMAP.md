## 首发定位与边界

首批用户是个人开发者和在获授权工作仓库中开发的程序员，优先支持 JS/TS、Python、Java。
个人免费版先完成“可靠检查 → 清楚解释 → 选择问题 → 批准修复 → 原检查复验”的流程，
并提供有用的本地记录。中文解释、本地历史和修复续办体验是待用户验证的差异化假设。

个人与企业的分界按工作方式划分：个人版保留有依据的检测、复核和修复复验；企业版以
组织权限、共享策略、集中风险、审批审计、规模化任务和部署支持形成价值。员工工作项目
的免费使用范围及 AI 数据出口需要在首发条款与说明中明确，本文不改写现行许可条款。

三种语言同时支持，不表示所有框架、任意封装或完整攻击链均已覆盖。每项能力需公开支持
输入、框架、证据范围及未知项；规则数量、成熟度标签和合成测试不能替代真实质量评估。

首发默认流程：安装与连接 → 首次项目检查 → 查看实际覆盖 → 选择问题 → 批准修复 →
复验。日常编辑使用增量检查；明确请求整库检查时执行整库检查，继续已有任务不重复扫全仓。

## 个人版依赖分析做到什么程度

先把“当前是什么版本、谁引入、版本在哪里控制、应改哪里”做好，再增强漏洞级路径分析。
依赖关系、函数调用和攻击者输入传播是三类证据，不能相互替代。

| 层级 | 应提供的证据 | 结论边界 |
| --- | --- | --- |
| 组件清单 | 直接/传递组件、实际解析版本、清单来源及覆盖缺口 | 声明版本不冒充已安装版本；不完整图保留未知 |
| 漏洞匹配 | 公告、受影响范围、修复版本及数据更新时间 | 版本受影响不等于当前应用已证明可被利用 |
| 使用线索 | 包引用和 API 使用位置 | 包被使用不等于对应漏洞函数可达 |
| 有限可达性 | 支持范围内的受影响 API、入口、调用边、参数与防护 | 未找到路径不表示不可达；缺少第三方或动态调用证据时说明缺口 |
| 当前影响判断 | 与具体产品版本、部署条件绑定的充分证据 | 证明当前不受影响与漏洞已修复分开；环境变化后重新评估 |

Maven 首先复用已有解析结果，并完善本地属性、父 POM、BOM 和版本约束归属。需要执行
项目相关包管理器、构建或联网解析时，通过明确的单独授权流程；自动 Hook 不执行这些步骤。
升级任务可按组件、版本和版本控制位置整理，保留全部漏洞明细，避免用户逐条重复修改。

有限可达性优先覆盖少量高频、高影响漏洞和支持框架内的路径。完整跨文件、跨库、反射、
动态调用及生产部署证据属于持续研发，不作为首发全覆盖承诺。专业 Skill 可按用户选择
继续核查具体问题；普通 Hook 不对每条依赖告警启动深度推理。

影响判断可借鉴 VEX 的版本化状态和依据：声明产品不受影响需要理由或影响说明，不能凭
搜索不到调用就自动隐藏组件漏洞。[OpenVEX 规范](https://github.com/openvex/spec/blob/main/OPENVEX-SPEC.md)

## 误报与接受风险

| 用户情况 | 处理方式 |
| --- | --- |
| 检测判断确实不成立 | 保存具体反证，人工确认误报，补安全写法回归 |
| 证据不足 | 保持待复核，补输入来源、调用或防护证据 |
| 问题成立但暂不修复 | 记录接受风险的理由、范围和有效期 |
| 测试或演示用途 | 记录场景，单独评估边界；不直接改成误报 |

原始发现保留，人工决定单独保存且可撤销。决定绑定问题、相关代码/依赖和规则版本；变化后
重新评估。只有用户明确创建的例外才影响提醒或本地策略，AI 的疑似误报不自动放行。尽量
减少行号变化造成的重复问题；关联不确定时请求复核，不移用其他问题的判断。

## 工具、规则和漏洞数据的更新规划

当前安装升级统一准备内部组件。后续把三种更新分别管理：

| 更新对象 | 规划 |
| --- | --- |
| 产品和检查引擎 | 使用发布清单中经验证的兼容版本、完整性校验与明确的激活时机，不盲追第三方 latest |
| 检测规则和专业指南 | 随产品发布的本地规则先保持稳定；独立分发需版本、签名、兼容性与缓存回退，不能修改授权边界 |
| 漏洞和恶意包数据 | 独立于产品发版检查到期状态；适配数据 schema，验证新缓存后切换，失败保留旧库并如实显示覆盖 |

后续后台数据维护采用到期/TTL 限制、并发锁、网络与磁盘预算、明确代理/离线设置和失败
重试。无需每次 Hook 下载数据库；维护任务与扫描分开，扫描记录实际所用的数据版本和
更新时间。首次尚无可用数据时不报“检查通过”；旧库可用于部分检查，但不冒充最新覆盖。
根据数据源更新频率和实测成本决定周期，不能照搬别家客户端 24 小时阈值作为漏洞库策略。
当前没有实现这个后台维护任务或远程产品更新服务，也没有按新公告自动重评已存组件。
现有本地发现与历史记录不等于可供持续重评的完整组件清单。

设计依据来自公开能力而非对私有工具链的猜测：Endor 的官方 governance 部署方案使用
默认 24 小时客户端更新检查、校验、并发保护，并有 POSIX 后台/Windows 前台的差异；这
仅说明该部署方案。[Endor 官方部署](https://github.com/endorlabs/mdm-scripts/blob/main/agent-governance/README.md)
其 SBOM Hub 公开说明可按新公告重评已有组件、无需重扫；对本产品的启发是让安全情报
具有独立生命周期。
[Endor SBOM Hub](https://www.endorlabs.com/use-case/sbom-hub-vex)
Snyk 提供自动管理 CLI、稳定/候选/预览渠道及固定版本；适合借鉴内部组件由产品管理、
兼容渠道明确的体验。[Snyk IDE 配置](https://docs.snyk.io/developer-tools/integrations/snyk-ide-plugins-and-extensions/unified-ide-configuration-dialog)
Trivy 分开引擎和数据库，并支持仅准备数据库及跳过更新的执行方式。
[Trivy 数据库](https://trivy.dev/docs/latest/configuration/db/)

## P1：个人版后续增强

| 有限路径证据 | 在重点漏洞及框架内展示真实调用/数据边、有效防护与未知环节；逐步扩展常见封装 |

| SARIF 导出 | 将已有规则、结果和位置导出为标准格式；有真实证据才填写路径，不通过转换虚构检测能力 |
| 基础 SBOM | 从可信组件 inventory 生成 CycloneDX JSON，包含无漏洞组件、版本、purl、依赖关系、来源与完整性说明 |
| 历史与变化重评 | 问题关联、撤销/到期例外、依赖变化和规则/数据版本变化后的重评 |

SARIF 是静态检查结果交换格式，可由支持的平台转换成代码告警；导出并不提升检测准确率。
[GitHub SARIF 说明](https://docs.github.com/en/code-security/concepts/code-scanning/sarif-files)
SBOM 是组件和关系清单，供版本比较、交付和新漏洞匹配使用，不能只列出 CVE 命中组件。
[CycloneDX SBOM](https://cyclonedx.org/capabilities/sbom/)
个人版基础 CI 允许用户配置自己的检查；组织强制策略、审批与共享门禁属于企业治理。

## 企业版阶段

保留本地 Runtime 的扫描、脱敏证据、修复交接与复验核心，另建组织管理服务。

| 企业能力 | 第一阶段 | 后续扩展 |
| --- | --- | --- |
| 身份与资产 | 组织、成员、角色、仓库归属和访问隔离 | SSO、SCIM、细粒度权限 |
| 集中风险 | 跨成员汇总、负责人、处理状态、期限和历史 | 跨仓库关联、趋势及资产重要性 |
| 统一策略与例外 | 策略版本、项目覆盖、例外理由/到期与操作审计 | 业务风险及合规映射 |
| CI/PR 与工单 | 一个主流托管平台、一个工单平台及组织门禁 | 批量修复、更多平台和 SLA |
| 企业网络与部署 | 受控上传、模型出口、检查工具及情报镜像 | 私有部署、保留备份、企业支持 |
| 供应链与 Agent 治理 | 稳定平台后建设包策略及 Agent/MCP/Skill 清单 | Package Firewall、许可证治理、深度可达性 |

当前单机工作区隔离、SQLite 和本地策略不等同于多租户权限或分布式任务系统。结果契约
先稳定仓库/提交、检查范围、发现身份、引擎/规则/数据版本、覆盖和验证记录，再实现组织
同步。组织策略仍保留明确批准具体修复的权限语义。

## 开发顺序与评估方式

先完成 P0 并邀请小范围个人试用，再根据真实失败和用户需求选择 P1；企业服务通过明确
组织试点逐步开发。每个工作包同时提交实现、有效回归及公开状态说明，保持源码测试、
实际扫描器、原生包和真实桌面验收分开。没有日期承诺、定时任务、外部部署或已完成
标记可仅由本文推导；实施需进入具体开发任务并通过对应验收。

## 后续产品对照评测：AICGSecEval

2026-10-12 用户确认：将 [Tencent AICGSecEval（A.S.E）](https://github.com/Tencent/AICGSecEval/blob/master/README_zh.md)
登记为后续产品效果对照评测的候选基础。当前状态为规划已登记，尚未接入或运行评测，
没有产品安全收益、性能或使用意愿的评测结论。

评测要回答：同一个 Agent 完成同样的开发任务，接入 AI Security Runtime 后，最终代码
是否更安全、风险处理是否更快、功能是否保持正常，以及增加多少等待和操作成本。
这项工作评估开发流程的效果，与现有 R1 规则检测质量评估分别记录。

### 对照设计与实施顺序

1. 执行前核对上游任务、功能测试、漏洞判定与许可，固定评测仓库提交、任务集和判定版本。
   先选择少量有明确功能验收与目标漏洞验证的任务，完成预试验，再确定正式规模和门槛。
2. A 组为 Agent 未接入 Runtime，B 组为同一 Agent 接入 Runtime；固定初始代码、需求、
   模型版本、基础配置、其他工具和资源限制。分别使用隔离副本，多次运行，完整记录失败、
   超时与未知结果；初始历史风险和开发新增风险分开统计。
3. 预先固定验收测试，由独立的功能测试、漏洞 PoC 或独立复核判定最终结果。Agent 不得
   改写这些判定条件；Runtime 自己的检出数或“通过”状态不能作为唯一效果证明。
4. 记录真实宿主 Hook、实际扫描、修复及复测证据。手动调用或模拟事件单独标注，不能
   替代真实开发中的产品介入；未执行、失败、覆盖未知和确认无风险分别记录。
5. 基准任务验证后，再扩展到 FlyCRM 等真实项目中的多文件功能开发，并安排用户试用。
   基准效果、真实开发体验与持续使用意愿分别评估。

### 最小指标与结论边界

| 维度 | 应记录的结果 |
| --- | --- |
| 安全收益 | 独立确认的目标漏洞与新增风险，误报、漏报及未验证范围；保留 A/B 原始结果 |
| 修复效率 | 从发现或确认到验证修复的耗时、成功修复率、修复轮次；企业试点另统计漏洞积压变化 |
| 功能保持 | 任务完成与功能验收通过率；删掉需求功能或阻止正常使用不能计为有效修复 |
| 产品介入 | 真实 Hook 触发、扫描范围、反馈是否被处理、修复和复测是否完成 |
| 使用成本 | 总耗时及新增等待、Token/调用成本（可取得时）、用户操作与误报处理成本 |
| 持续使用 | 真实用户试用后的继续启用情况与原因；不能由基准成绩推导安装意愿或付费意愿 |

具体验收阈值在预试验后预先确定，正式结果按任务、语言、漏洞类别和实际覆盖分层报告。
基准未覆盖的业务逻辑、框架或环境保留未知；有限任务的结果不扩展为全项目安全保证。
