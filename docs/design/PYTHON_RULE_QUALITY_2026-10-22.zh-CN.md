# Python 误报与漏报第二轮验证

日期：2026-10-22。当前源码内置 `ai-security-core 1.4.2`，仍为 68 条独立规则、60 条默认启用。沿用默认仓库规则和用户本地 `--rules`；本轮没有扩大跨文件分析、增加运行依赖或修改基准源码。

## 变更与边界

- 原代码注入规则补充 `exec`，保留现有 `eval`，规则版本为 1.3.0。
- 本地证明识别函数内新建、未逃逸的 ConfigParser 固定选项，按标准配置键大小写规则处理。外部读取、插值、动态键、别名修改、未知调用、带参数构造和全局导入绑定均不作为固定值证明。
- eval/exec 仅识别完整的字符串字面量防护：同时要求首尾引号、内部没有同类引号，拒绝分支以无条件 return/raise 结束；缺项、使用 and、仅记录日志、改值后执行、拼接后执行均不放行。这种防护不适用于 Shell 或 SQL。诊断使用 `EXACT_STRING_LITERAL_GUARD`，与常量过滤区分。
- SQL 规则 1.3.2 补充字典写入传播，并避免其他键的后续写入抹去已有污点。本地常量模型区分安全键、固定覆盖、`dict.get` 和常量缺省值；参数绑定仍不算查询文本拼接。

这些是标准 Python 字符串、普通本地字典及 ConfigParser 语义下的有限模型，不建模运行时替换、定制字符串子类、任意外部包装函数或全部容器操作。规则的来源/传播/API 模型不能替代完整语言语义。无法建立模型内证明时保留原告警；只对内置规则启用过滤，自定义 `--rules` 不使用它。

仍沿用每文件 250 KB、20000 AST 节点、30000 步、0.2 秒软预算，以及每次扫描 1 秒累计软预算；文件读取另有 80 文件、2 MB 上限。扫描前后源文件摘要必须匹配，读取失败、解析失败或预算不足保留告警。没有执行被扫描的程序。

## 没有采用的扩大方案

曾试验 Cookie/Header/getlist 输入流向 codecs.open/io.open，带来 3 个新增真阳性，但也给安全常量分支样本 00004 增加了误报。本轮已撤回这些路径规则改动，没有把未能稳定区分的覆盖扩展纳入交付。

剩余问题包括外部安全包装函数、固定路由语义、外部基础目录与局部路径的组合、命令参数列表内隐式 Shell 执行，以及 Flask HTML 返回值语境。没有仅凭防护函数名称、路由名称或“未跟踪到污点”就判为安全。下一轮应继续逐类建立正反例，不能为了消除剩余数字扩大过滤。

## 回归与复现

最终无并行测试负载的三轮 A/B 使用相同 128 文件基线批次设置，每次重新执行扫描；普通扫描默认 40 文件批次没有改动。顺序为 before/after/after/before/before/after。前侧耗时为 14.706、6.357、6.243 秒，后侧为 6.269、6.190、6.543 秒；中位数 **6.357→6.269 秒**，本机约 -1.4%，应理解为没有观察到明显变慢，而非稳定加速承诺。首轮包括冷启动和版本探测，不将它与单次热启动比较。Python 三轮的检测结果完全一致。

本地证明累计耗时分别为前侧 0.125、0.125、0.109 秒，后侧 0.125、0.187、0.172 秒，中位数增加约 47 毫秒；仍在原 1 秒软预算内。之前与其他测试并行的一组曾观察到总耗时约 +6.1%，也保留原始记录，说明小差异受本机负载影响。不能外推为大型项目的最坏耗时保证。

相关回归去重共 198 项、另有 6 项 subtest 通过；原始规则门禁为 68 条规则、221 个正例、193 个反例。额外产品入口门禁验证 9 个 SQL 字典正反例，覆盖安全键、危险键、覆盖写入、get、缺省值、别名及绑定参数。原始 YAML 门禁与产品过滤门禁分别执行，不把后者的过滤效果冒充为原始引擎能力。
