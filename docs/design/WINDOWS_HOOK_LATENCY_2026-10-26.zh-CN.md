# Windows 分页路径与编辑 Hook 耗时修复

日期：2026-10-26。基于 `8f22b01` 的本地开发改动，Runtime 版本仍为 0.3.9。

## 改动与完整性边界

1. 分页快照的写入、普通读取和严格只读读取统一使用已有 Windows 扩展路径处理逻辑。URI 保留原生长路径，并正确转义中文、`#`、`%`；只允许 `ro`、`rw`，缺少数据库时拒绝打开，不能隐式创建。原路径、链接、私有权限、身份、配额、签名、页/正文哈希、journal 与只读检查保留。生产复核控制的 `rw` 连接也使用同一处理逻辑。
2. `RECORDED_PENDING` 编辑回执仅读取认证任务头，不再展开 baseline/end 的全部分页内容。回执仍表示活动已记录，不能证明扫描或源码复核完成。完整源码读取、损坏拒绝及收尾义务仍由原流程执行。
3. `hook_total` 和 `duration_ms` 移到返回数据准备完毕的边界，覆盖任务记录、反馈和交付回执。新增 `task_recording`、`feedback_processing`；总时间不包含传输序列化、宿主等待或模型时间。

未修改扫描目标规划、扫描器规则、捕获/交付容量、旧任务策略或原始基线语义。新任务仍在编辑时记录、收尾时检查；旧逐次扫描任务保持原行为。

## 回归结果

修复前，原有 `test_headers_keep_control_and_default_reads_keep_complete_sources` 在本机 Windows/Python 3.12.10 上复现 `invalid uri authority: %3F`。

最终相关组分别完成：

- URI、分页存储、只读 reader、认证头及既有长路径用例：74 项通过、1 项 POSIX 权限/链接断言跳过。
- Codex Hook、任务反馈及生命周期：74 项通过、2 项系统不允许创建符号链接的夹具跳过。
- 当前生产复核控制路径：11 项通过；3 项依赖另一套捕获发布能力的参数分支未列入该通过数。
- 合计 159 项通过、3 项跳过；组间不重复计数。依赖检查和 `git diff --check` 通过。

计时回归使用确定性时钟，分别在任务记录、反馈生成、交付回执注入 250/200/400 ms，最终总时间必须为 850 ms；原先在任务记录前停止计时的实现无法满足该断言。

WAL 竞争用例仍在真实只读连接前切换 journal，继续断言拒绝打开、零 reader sidecar、存储未被改变；仅将拦截器从旧 URI 字面值改为实际 URI 生成函数。

首次扩大到尚未完成 Windows 适配的基础模块时，得到 171 通过、83 失败、4 跳过、18 错误。其中本批 URI 改变导致 WAL 夹具未命中真实连接的用例已修正；其余失败涉及 typed scratch 的 POSIX 限制、metadata 的目录 fsync、capture publication 的 POSIX 权限检查及 product epoch 的平台能力限制。未修改这些平台护栏或把整个扩展组标为通过。在未修改的 `8f22b01` 独立副本上，metadata、capture publication 和 product epoch 的三个代表项分别复现相同错误（2 失败、1 setup 错误）；没有宣称逐项复现了所有扩展失败。

## 安装及本机测量

完成上述定向验收后更新现有源码开发安装与本机 Codex 全局接入。构建为 `ed80e1897bc927419a12a366f40eef3ff78a200690c607588b71c39638afe8e8`；新独立 MCP 按实际安装配置启动，构建一致、九项必需接口齐全。当前聊天接口随后也报告同一源码构建；可编辑安装的源码身份不能单独证明所有已导入 Hook 模块已重载，仍按安装回执完全退出并重开 Codex。

测量脚本：`scripts/benchmarks/hook_latency.py`。使用已安装 Runtime 的真实 Codex Hook、真实签名任务/活动记录和私有分页存储，合成文件清单；各组先暖机一次，再按相反顺序交替执行 10 轮。对照臂只恢复旧 `RECORDED_PENDING` 全量任务读取分支，其余代码与完整计时边界相同。未经修复的原构建无法在本机创建这些分页，故这不是原二进制与新二进制的完整对照，也不是桌面聊天/扫描器/模型耗时。

主指标来自函数外侧墙钟，避免使用原先不完整的 Hook 自报耗时作对照。

| 合成清单 | 原全量读取分支中位数 | 当前认证头分支中位数 | 中位数下降 | 最大值（原/当前） |
| --- | ---: | ---: | ---: | ---: |
| 1001 文件 | 594.609 ms | 93.041 ms | 84.35% | 693.209 / 144.842 ms |
| 6000 文件 | 3470.356 ms | 102.652 ms | 97.04% | 3690.922 / 175.126 ms |

任务读取部分中位数分别为 521.306→19.823 ms、3344.947→20.949 ms。夹具建立时间单列为 435.607/1809.474 ms，不混入编辑 Hook 延迟。10 轮样本不报告 P95。

每组 22 次真实活动记录（含两次暖机）全部保留；任务控制数据库字节和开始/结束快照映射均未改变。扫描器调用为零，这是 TASK_CLOSEOUT_V1 编辑阶段的既有行为；回归测试另外验证了旧策略逐次扫描和新策略收尾扫描，没有为了测量跳过其正常扫描义务。

本机原始计时输出保存在忽略目录 `.test-tmp/hook-latency-20261026/`。可重新执行：

```powershell
.\.venv\Scripts\python.exe scripts/benchmarks/hook_latency.py --files 6000 --repeats 10
```
