# 批次安全审查实验版本的同场景对照

实验版本保留同步 Hook 静态检查和现有任务末静态检查。在同一批源代码、相同编辑顺序、相同静态规则下，对比原流程和新增批次流程的兼容性、扫描调用及编排开销。

对照基线固定为 `b3817b1168aa7d632e94afa3c4d3b1214bd607d6`。原仓库不因本次对照发生修改，实验代码位于独立 worktree。脚本为两侧分别启动 Python 子进程，使用各自的 `src`，不在同一进程中切换导入缓存。

## 测试包含什么

1. 初始化相同 JavaScript 项目，建立相同的 Hook 基线。
2. 开始开发任务，修改订单入口，真实执行同步 Hook 静态检查。
3. 实验侧固定第一批快照、读取快照证据、提交明确标记为 fixture 的候选。基线侧继续原流程。
4. 引入 `new Function` 动态执行，真实执行第二次同步 Hook 静态检查；实验侧固定并提交第二批。
5. 两侧按原接口完成任务末静态扫描、最终上下文读取和任务级提交。
6. 核对最终文件 hash、规则身份、静态调用次数、扫描范围、发现规则、最终版本和旧接口状态。

静态部分使用产品内置的 `native-js-function` 扫描器，读取真实项目文件并执行真实词法检查，没有模拟扫描返回值。该扫描器只覆盖特定 JavaScript/TypeScript 动态执行语法，不代表整个产品的静态规则组合。

AI 分析提交是固定测试数据，用于验证协议、版本、证据和汇总通路，**没有实际调用模型**。本脚本不能证明模型准确率提高、误报减少、真实子 Agent 提速或生产可达性。结果 JSON 将这些指标记录为 `NOT_MEASURED`。

## 运行方式

在实验目录执行，输出必须使用一个不存在的新目录：

```powershell
$env:PYTHONPATH = "$PWD/src"
& C:/Users/24170/Desktop/AI-security-check/.venv/Scripts/python.exe scripts/compare_batch_review.py --baseline C:/Users/24170/Desktop/AI-security-check/.test-tmp/batch-review-baseline --experimental "$PWD" --output "$PWD/artifacts/batch-comparison" --iterations 3
```

脚本默认做三轮对照，轮流交换两侧执行顺序。输出 `comparison.json` 保存原始执行记录、中位耗时、逐项兼容性结论和限制；每轮两侧的 `result.json` 保存可追溯的本地记录。时间只表示真实本地静态执行和编排耗时，不解释为模型并行收益。

每侧执行前后均校验实现源码树的 hash，避免在对照期间修改实现却将混合版本的结果记为同一版本。对照的 `passed` 只表示列出的流程和覆盖一致性检查成立；如果静态结果本身是 `PARTIAL`，不会因此变成完整安全核查通过。

`tests/test_task_security_batch.py` 负责不可变快照、源文件和关联文件过期、新增文件的整任务复核、共享上下文预算及最终版本覆盖的单元验收。`tests/test_batch_review_comparison.py` 负责对照结论校验，避免扫描缺失、范围差异、版本过期等情况下错误判为通过。

## 为什么实验阶段保留任务末静态扫描

Hook 当前保存的状态用于增量反馈与历史缺口跟踪，没有建立可合并的完整证明，证明每份静态结果确实覆盖最终源码 hash、规则身份和任务保留复查范围。因此首版继续按最终任务范围扫描，既能维持原来的末次版本保证，也能把本次实验的变量集中在 AI 批次编排上。

这不是永久要求重复扫描。后续只有在可以验证每个最终文件和规则版本都由有效静态证据覆盖时，才能安全复用 Hook 静态结果；新增、删除、重命名、修改后撤销、失败/延期 Hook 和规则变化都必须单独证明覆盖。

最终源码下完成 3 轮、6 个独立子进程对照。每轮 14 项流程检查全部成立，共 42 项；每侧均为 2 次编辑 Hook 静态调用、1 次任务末静态调用。两侧各轮最终文件 hash、规则身份、扫描范围、发现规则和旧任务末接口状态一致；实验每轮成功派发 2 批，批次准备、读取和提交没有额外启动扫描。

最终第 1 批为 `INTEGRATION_RECHECK`：其自身文件和已读取关联文件仍匹配，但后续任务已有另一批改动；第 2 批为 `CURRENT_REUSABLE`。两批都保留 `PARTIAL` 覆盖，不被当作完整最终审查复用。任务末重新读取最终改动和关联文件，保存完整的整合字段、当前证据与历史候选处理记录；三个最终任务均为 `COMPLETE` 且 `current_version=true`，这里的 COMPLETE 是提交生命周期完成，覆盖仍为 PARTIAL。

预集成探针曾发现重复指南占用上下文预算：两批消耗 45,586 字节，最终材料再消耗 18,326 字节，使首条最终证据读取即触发 64,000 字节上限。实现随后改用紧凑批次方法，仍绑定父指南版本，完整任务末方法只提供一次；没有提高总预算、重置额度或减少必要源码读取。正式三个样本均为批次累计 23,638 字节、最终累计 44,602 字节。失败探针和前一实现的对照保留为历史诊断，没有混入最终样本。

静态部分执行真实内置 JavaScript 动态执行规则，最终每侧都得到 1 个对应静态候选。未启用完整静态引擎组合，聚合状态与覆盖均为 `PARTIAL`，故本报告不能认定完整安全检查通过。固定 AI 候选只用于验证协议，不计入模型准确率、误报率或实际发现能力。

源文件变化、关联文件变化、新增文件、删除前证据、元数据变化、策略变化、共享预算和最终覆盖的边界行为，由 `tests/test_task_security_batch.py` 与 `tests/test_batch_final.py` 分别验证；它们与这里的相同编辑序列对照分开记录。

## 最终回归

最终冻结源码下，批次、只读 worker、真实 CLI/stdio、最终证据、对照判定、原任务核查、条件性风险、任务盘点、同步 Hook、全局工作区路由、Cursor 权限及原 MCP 流程的选定回归共 **257 项通过、1 项跳过**，耗时 413.40 秒。原始记录见 [JUnit XML](../../artifacts/batch-regression-final.xml)。

测试临时项目位于仓库外的短路径，避免被祖先 Git 项目吞并或触发 Windows 路径长度限制。首轮使用工作树内深路径产生的 8 个环境失败已单独排查；原版对应的 9 项回归在仓库外短路径下全部通过，实验版最终整组也通过。没有为消除这些环境问题修改业务逻辑。

其中只读 worker 使用真实独立 Python CLI/stdio 进程验证工具清单、125 行分页、旧快照隔离、拒绝扫描/提交/重绑定、实际 Hook 状态目录及同名模块覆盖防护；这证明受限读取进程的边界，不等于已经验证 IDE 宿主自动创建并行模型 Agent。
