# Python 漏报第三轮验证

日期：2026-10-22。源码内置规则包更新为 `ai-security-core 1.4.3`，仍为 68 条独立规则、60 条默认启用。只修改 Python SQL 规则的局部传播模型；用户本地 `--rules` 流程、跨文件分析范围、扫描预算和运行依赖均不变。已发布安装包不随源码自动更新。

## 本轮实现

SQL 规则版本从 1.3.2 更新到 1.3.3。在已出现 `configparser.ConfigParser(...)` 构造的局部代码中，识别相邻的 `set(section, key, value)` 和 `result = get(section, key)`，将不可信 value 传播到 result，再沿现有 SQL 查询文本规则检查。section 和 key 必须匹配，写入和读取之间不能夹有其他语句。

最初试验过将污点传播到整个配置对象；最终采用按同一键匹配的窄模型，防止读取另一个安全键时新增告警。安全键、不同 section、固定值覆盖和参数绑定反例直接通过原始引擎门禁，不依赖产品常量过滤来消除新增告警。配置对象在 get 后改为固定值，不会把已经复制到普通字符串的危险值判为安全。

这是有限的标准 API 模型，不是 ConfigParser 的完整实现：不新增跨语句间隔、大小写变体键匹配、任意别名、外部包装函数、插值或任意 set/get 对象的专门传播。没有修改现有本地常量证明器或增加新的 AST 遍历。

## 保留边界

路径规则尝试了表单 getlist、codecs.open/io.open 和切片传播，未能在固定基准中得到可靠新增命中，本轮未合入；路径 YAML 与 1.4.2 逐字节一致。此前引入误报的 Cookie 路径扩展也未采用。

剩余 SQL 两例涉及外部请求包装函数；另有隐式 Shell 参数列表、Flask 返回 HTML 的语境、路径容器和字符串切片。后续仍应为每类建立独立正反例，不把“没有跟踪到污点”当成安全，也不以减少漏报总数为由扩大跨文件范围或笼统增加 sink。

## 回归与复现

无并行测试负载的 Python 三轮 A/B 顺序为 before/after/after/before/before/after，采用相同 128 文件基线批次配置；普通扫描的默认批次没有改动。前侧耗时为 17.139、8.976、7.385 秒，后侧为 7.139、9.123、7.881 秒，中位数 **8.976→7.881 秒**。首轮包含冷启动和版本探测，这组结果只支持“本机未观察到明显变慢”，不代表稳定加速或大型项目最坏耗时保证。三轮逐样本结果完全一致。

常量证明器的源码逐字节未变，累计证明耗时前侧均为 0.172 秒，后侧为 0.187、0.250、0.188 秒；中位数增加约 16 毫秒，仍在既有 1 秒累计软预算内。

同批其他语言通过同一 SemgrepAdapter 的前后对照：DVWA 155 个 PHP 文件仍为同一组 33 条命中；NodeGoat 19 个 JS 文件仍为同一条 SSRF；GoVWA 20 个 Go 文件的 YAML 命中仍为零。该 Go 对照只覆盖 YAML 引擎，本轮没有重新测量原生 Go SQL 链路，不能把零 YAML 命中解释成无漏洞。除 SQL YAML 和 catalog 版本外，整个规则目录与 1.4.2 快照逐字节一致。

原始规则门禁通过：68 条规则、223 个正例、198 个反例，Semgrep 1.178.0。产品入口门禁共 17 个 SQL 字典/配置用例，包含本轮新增 8 个配置正反例。相关回归去重 198 项、另有 6 项 subtest 通过；其中许可证清单版本未同步造成的一次失败已修正并单独复跑通过。
