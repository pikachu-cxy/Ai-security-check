# Java / Python 第 4 轮优化与 Semgrep 官方规则对照

日期：2026-10-16（北京时间）。本轮为源码候选：核心规则包仍为 1.3.1，独立数据流分析器为 1.2.0；尚未构建新安装包。

## 本轮采用的改进

- Java：保留循环条件分支中 `break` 的退出状态，使输入能够继续传递至循环后的本地调用和 SQL 操作；隔离方法、switch 与循环的退出状态，避免把退出分支污染到继续执行的分支。
- Java：已解析本地方法声明的 JDBC 返回类型可补充连接类型；不根据名字推断，不把确定的 null 或本地同名类当 SDK。请求 Enumeration 仅建模一个抽象迭代，零次路径与未覆盖的后续迭代仍明确保留。
- Python：补充 `getlist` 元素、切片和 `with` 上下文表达式；保留 `Path / value`、`resolve`、`joinpath` 等操作中的路径污点，以及跨文件的读取、存在性查询和 stat 调用。
- Python：在开发集通过误报门槛后，仅将已解析的 `io.open`、`codecs.open` 提升为默认的单文件路径子集；其他单文件路径仍为实验范围。原有跨文件路径追踪保留。
- `resolve`、`'../'` 检查、字符串 `startswith` 均没有被当作通用安全证明；保留独立危险/安全对照和同名模块反例。

本轮增益适用于功能级、项目级扫描，未加入 quick 或每次文件编辑 Hook。
规则身份数不因 SDK API 或数据流分支增加而增加：核心 55 条、默认 47 条、原有 8 条 Java 实验规则关闭状态不变；
独立数据流规则为 6 个身份、默认 3 个，仍不声称完整程序分析或“未发现即已修复”。

## 本地规则来源

当前核心 catalog 的 55 个记录均声明 `FIRST_PARTY`、Apache-2.0，`derived_from` 为空；
项目的第三方声明也记录为独立编写。独立 AST 数据流分析器同样是本地实现。
Semgrep 是静态规则的执行引擎，不等于产品已经默认加载官方规则库；词法、密钥与依赖扫描是另外的能力。
这里确认的是仓库的实现和来源记录，不是独立法律原创性鉴定。

## 官方规则对照方法

采用两份独立快照，均通过本机相同的 Semgrep CE 1.178.0 引擎执行：

1. 官方托管的公开仓库 `semgrep/semgrep-rules`，提交 `17e31e11ebac99fb7dfe1cd288f7a32151b6f3f9`。
2. 官方 Registry 的 `p/default` 公共下载快照，SHA256 `f028d6b0eaa186ae43fec92e5fdac22c03ed41ddd4dca359c54cf6a262de5492`。

按 CWE-22/23/36/73/89 和 Java/Python 语言声明自动选择全部对应规则，没有按测试结果挑规则。
公开仓库选中 Java 17、Python 29 条；默认快照选中 Java 17、Python 30 条；其中 Java SQL 14 条，Python SQL 23 条。
默认快照共返回 1074 条公共规则，另有 `missed=1856` 字段；未取得的规则不计为已测试，也不推测未返回的原因。

保留原规则体、选项、许可和元数据；只有公开仓库中可能重复的短 ID 加路径前缀，默认快照的已发行 ID 不变。
所有扫描均为离线规则文件、明确目标文件、关闭遥测与版本检查，不上传项目源码，不运行目标代码。
前后核对目标哈希，逐批检查退出状态、错误、实际扫描文件与 `time.rules` 中适用规则的执行证明；所有比较批次完整。
两份快照在本批标签范围内得到相同计分，不代表规则内容完全一致。

## 官方与自写效果

每格为“TP / FP”，分母和阴性样本与前面的同源对比相同。

| 范围 | 自写核心规则单独运行 | 第 3 轮产品组合 | 第 4 轮产品组合 | 官方 p/default 的对应规则，CE |
| --- | --- | --- | --- | --- |
| Java SQL | 19 / 10 | 135 / 10 | 163 / 10 | 253 / 170 |
| Python 路径 | 2 / 6 | 4 / 6 | 14 / 6 | 2 / 2 |
| Python SQL | 1 / 0 | 5 / 0 | 5 / 0 | 5 / 0 |

官方默认规则的 Java SQL 召回率为 93.0%、精确率 59.8%；本轮产品组合为 59.9%、94.2%。
Python 路径官方默认规则召回率为 3.1%、精确率 50.0%；本轮组合为 21.5%、70.0%，但绝对误报数仍高于官方的 2 个。
自写核心规则单独运行明显较弱，不能用加入独立数据流后的成绩声称 YAML 规则本身优于官方。
这仅比较两种漏洞类别在这些基准上的结果，未覆盖所有规则、语言漏洞类别或商业产品能力。

规则级观察：

- 官方 Java `tainted-sql-from-http-request` 检出 234 个阳性、命中 143 个阴性；`jdbc-sqli` 为 97、81。两者存在重叠，不能相加。
- 抽查 `BenchmarkTest00104`：整数条件恒真，SQL 实际拼接常量，说明分支常量传播是控制该类误报的重要方向；不能把这个解释泛化到全部 170 个误报。
- Python 的格式化 SQL 和 SQLAlchemy 执行规则在本样本检出了全部 5 个阳性；路径规则仅覆盖了少量模式。
- 官方独有 Python 阳性 `BenchmarkTest01196` 是 Header 输入经 f-string 到 `with open`；本地路径核心规则的 Header 输入仍未建模，原生分析又尚未默认开放一般单文件 `open`，因此仍漏报。此处只记录缺口，没有直接复制官方规则。
- Java 官方独有样本中的请求名 Enumeration、带 `&&` 的 while、索引 for 以及动态工厂，是后续原生模型需要补齐的具体方向；当前单次 Enumeration 子集仍不覆盖这些组合。

按检出集合直接合并，本批 Java 可达 TP 266 / FP 170，Python 路径 TP 15 / FP 6，Python SQL 不变。
这只是集合运算结果，没有接入产品。官方补充了 Java 103 个阳性，本地组合也检出官方未报的 13 个 Java 阳性；
Python 官方只多出 1 个阳性，本地组合另有 13 个官方未报阳性。直接合并会把 Java 的误报成本带进来。

## 如何借鉴

保留自写规则作为可控默认层，继续独立实现输入来源、路径 API、容器和调用绑定；补充官方测试中暴露的覆盖缺口。
对于范围宽的查询审计模式，先作为离线对照或用户自行提供的规则做复核，不能把任意字符串查询直接认定为可利用注入。
下一轮优先补 Java Enumeration 条件与索引循环、Python Header 到一般 `open` 的受控范围，以及动态工厂和真实框架调用链。
新的规则推广仍需开发组门槛和独立对照，不能把当前回归组称为新盲测。

官方文档说明 CE 的分析范围主要是单函数，商业 Semgrep Code 才提供跨函数及跨文件能力。
这次没有登录、购买、安装或测试商业 Code/Pro 引擎，不能据此比较商业版跨文件检出率。
Semgrep Rules License 规则的许可规定仅限自身内部业务用途，不允许分发或作为服务提供给他人；默认快照还含其他作者和许可，逐条保留元数据。
本轮全部第三方快照只留在忽略的本地评估目录，不进入产品规则和分发包。
本轮独立实现和独立正反例没有移植官方规则体。

参考：[官方默认运行方式](https://docs.semgrep.dev/running-rules)、[公开 CE 规则仓库](https://github.com/semgrep/semgrep-rules)、
[CE 与商业跨文件分析边界](https://docs.semgrep.dev/semgrep-code/semgrep-pro-engine-intro)、[规则许可](https://semgrep.dev/legal/rules-license/)。

## 回归与检查边界

最终相关回归：251 项通过、6 项子测试通过；包括新增的独立跨文件路径、切片、with、循环退出、同名模块、null 返回、规则选择与执行证明反例。

最终使用独立临时仓库；修正脚本格式处理，合规测试改为稳定错误码并显式断言未下载，没有削弱许可限制。

开发任务的自动安全核查未完成：开发版源码更新后托管构建身份变化，完成检查时被接入就绪门槛拦住，扫描尚未运行，后续有界代码复核未执行。
没有通过另建编辑后基线、补造事件、补扫或循环修复接入来抹去该缺口。基准和回归成绩不替代这项检查。
