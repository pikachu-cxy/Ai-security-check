## 分成两个集成目标

### 目标一：核心批次能力进入正式代码，默认关闭

这部分可以单独评审和合入：

- 批次不可变快照、任务共享预算、单个运行批次与可合并待处理批次。
- `CURRENT_REUSABLE`、`INTEGRATION_RECHECK`、`STALE` 及覆盖不足的判定。
- 绑定任务、批次、会话的只读快照上下文接口。
- 最终版本清单核对、跨批次整合、历史候选处置和最终证据约束。
- MCP 可选工具、CLI 显式开关和兼容旧任务流程的入口。
- 合法 Codex 托管 worktree 的准入修复及不泄露原始路径/异常的错误诊断。

当前默认行为：

| 入口 | 默认行为 |
| --- | --- |
| `create_server(include_batch_review=None)` | 仅当环境变量 `SECURITY_RUNTIME_BATCH_REVIEW` 严格等于 `1` 时启用 |
| CLI `mcp` | 需要显式 `--experimental-batch-review` 才设置开关 |
| Global MCP、工作区池、`runtime_info` | `include_batch_review=False` |
| Hook 静态检查 | 保持同步执行 |
| `finish_security_task` | 保留任务范围的同步静态检查 |

合入本目标不等于后台子 Agent 已默认运行，也不要求同时改变安装程序生成的宿主配置。既有入口应继续走既有任务结束审查流程。

### 目标二：宿主适配器产品化，再灰度后台派发

真实 Codex 派发目前位于 `scripts/codex_readonly_host.py`、`scripts/codex_app_server_client.py` 及比较程序中。核心 Runtime 生成 `reviewer_handoff`，尚未自动调用模型。比较脚本能运行真实模型，不代表日常安装已具有相同的后台调度路径。

默认后台运行前，还须完成：

1. 将已验证的宿主适配器整理为受支持的产品模块，并纳入源码安装和独立程序打包。
2. 把有意义的改动检查点、后台任务启动、候选提交、超时取消和任务结束前的有界等待接入真实宿主生命周期。
3. 保持专属 `security_review` 命名空间和唯一绑定读取回调；禁止继承父 Agent 的项目写入、命令执行、网络及再次派发能力。
4. 使用实际执行探针核验宿主二进制与隔离配置，不能由调用方传入的 `ready` 布尔值、工具描述或只读提示词授权派发。宿主仍声明的禁用执行包装和问题工具，应如实记录；客户端不得转发问题或审批 UI。
5. 宿主能力不足、证明失效、模型失败或预算不足时，保留现有任务结束审查，报告未覆盖范围；不得静默替换成继承完整工具的子 Agent。
6. 记录每次模型调用、工具读取、耗时、模型标识及实际使用量。费用不可得时保留未知；API 等价估算必须与实际扣费分开呈现。

目标二应有单独开关和回退路径。不要仅把现有批次工具开关改成默认开启，就宣称已完成默认后台派发。

建议在新的、干净的集成 worktree 中执行以下顺序；这些步骤尚未执行：

1. 记录实验最终 SHA、正式目标 SHA 和对比报告；确认原工作目录的其他未提交改动不在本次集成范围。
2. 核验远端默认分支及发布目标，更新目标分支信息。不要在原来的脏工作目录切分支、reset 或覆盖文件。
3. 从核验后的正式目标提交建立 `codex/batch-review-integration`。
4. 按上述顺序 cherry-pick 实验提交，排除 `b3817b1`。如采用 squash，所生成的补丁也必须以 `b3817b1..实验最终SHA` 为实验改动边界，再应用到正式目标上。
5. 逐项解决冲突，保留正式分支更新后的数据流和规则能力；核对集成 diff 只包含实验功能及其必要修复。
6. 完成下面的门禁，在 PR 中记录实际结果，再合入目标分支。合入后另行发布和灰度，不能把本地合并视为安装版本已更新。

## 冲突重点

`host_guidance.py` 是当前已知的交叉修改点。正式 `33b6f40` 将 `bounded_dataflow` 从 `v1.2` 更新到 `v1.3`；原工作目录该文件还存在后续未提交修改。集成应保留正式数据流能力标识，并按开关追加批次指导，避免覆盖已有指导文字。

`task_security.py`、`global_integration.py` 和配套 Skill 在 `b3817b1` 与已核对的 `33b6f40` 之间内容相同，但后续主线仍可能修改它们。应按目标分支的最终 diff 判断冲突，不能提前保证零冲突。`global_mcp.py`、`mcp_server.py` 和 CLI 的最终审查、准入及参数校验也需作为组合行为验证。

## 集成与发布门禁

| 门禁 | 必须具有的证据 |
| --- | --- |
| 默认关闭兼容性 | 新安装及未显式启用的旧配置不增加批次工具，不启动模型；旧 Hook、任务结束静态检查和最终审查可正常完成 |
| 批次正确性 | 快照稳定性、改动合并、共享预算、证据分页、过期结果、修复/回退/删除、最终版本变化及终态拒绝的针对性测试通过 |
| 托管工作区准入 | 合法 managed worktree 可完成真实 MCP 开始/结束任务；内部状态目录及不合法链接仍被拒绝 |
| 宿主执行隔离 | 实际安装宿主的正负向执行探针通过，业务读取确实走绑定回调；二进制或隔离配置变化使旧证明失效；未知请求不能获得权限 |
| 真实模型比较 | 同一组任务、相同模型及推理配置、明确开发节奏和预算；报告真实重叠时间、最终有效发现/误报、过期候选及实际 token，不能用 fixture 输出代替模型结果 |
| 比较结论 | 每项候选有人工或可复核代码证据处置；明确样本数、运行顺序、失败、重试和成本缺口，不把小样本观察推广成普遍收益 |
| 产品化与交付 | 适配器进入实际安装路径，源码和独立程序均可启动；宿主失败能回到既有结束审查；具备关闭开关和恢复旧配置的可验证路径 |

目标一可在自身门禁满足后保持关闭开关合入。目标二只有在实际安装路径、真实模型证据和回退验收都完成后，才适合面向少量任务灰度；是否改为默认行为，应依据灰度期间的结果再决定。
