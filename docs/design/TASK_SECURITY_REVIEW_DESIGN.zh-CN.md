# 开发任务结束安全核查实现方案

历史设计日期：2026-10-13。以下实现状态、固定额度与旧接口记录描述当时版本，已被当前 [v3 唯一协议说明](../TASK_REVIEW_V3_ONLY.zh-CN.md)取代，不能用于新版 Runtime 的调用或恢复。当前默认仅 3，旧任务只读且不迁移；get_task_security_review 只查询历史，不恢复任务。完整架构与状态见[本批实现记录](../ARCHITECTURE_UNIFICATION_COMPLETION.zh-CN.md)。

目标是在 Agent 完成一次代码开发任务时，把该任务的实际改动、基础扫描结果和必要上下文交给宿主 Agent，按快速核查方法发现更深一层风险。普通聊天、解释问题和只读操作安静结束。安全核查作为开发任务的一个步骤，结果融入任务总结；内部计划不成为独立聊天消息。

## 产品边界和触发方式

Qoder 官方将轻量扫描描述为任务临近完成时建议启动，用户可以忽略建议而不影响后续流程；深度扫描侧重增量代码的跨文件数据流。这里借鉴分层和任务边界，不推断其内部实现或独立准确率。[官方安全说明](https://docs.qoder.com/qoder-security-guide)

首版先采用明确的任务编排：宿主 Agent 在准备执行已授权开发任务、首次修改代码前登记任务，在开发完成、准备总结时提交结束核查。用户无需操作内部接口或发送“继续”。项目可以选择任务结束自动核查或按需核查；普通 Stop 事件不代表开发任务完成。

没有任务记录、没有实际源码或安全相关配置变化，结束事件返回空的用户反馈，不开始模型审查，不重复旧风险提示。只读工具事件不创建新代码任务。安装组件准备、原风险复查和开发语义核查分别管理，不能互相拉起聊天。

当前宿主如果没有可靠的任务事件，先通过已有 MCP 指导和开发工作流约定 begin 和 finish。Agent 漏掉 begin 时明确范围未绑定，只保留实际执行的基础检查或经用户选择的当前 Git 差异核查；不能根据每次回复结束猜出完整任务范围。该配合能力需要真实宿主验收。

## 用户应看到什么

| 情况 | 用户体验 |
| --- | --- |
| 普通问答或只读查询 | 无新增安全消息，无结束扫描续跑 |
| 开发后没有实际改动 | 不启动任务核查 |
| 任务核查完成且没有需要处理的候选 | 任务总结中至多一行说明本次改动已检查及范围；详细结果保存在本地 |
| 新风险有静态证据支持 | 在任务总结中给出位置、触发条件、影响、修复建议及未知项，等待明确选定后修复 |
| 高影响疑点仍缺上下文 | 显示待核查及需要补充的事实，不包装成已经证实的漏洞 |
| 检查中断或预算不足 | 简短说明这次任务哪些范围未完成，记录可恢复任务；不阻止后续普通聊天 |
| 相同风险或有效结果重复出现 | 复用记录，不因用户再次说话而重复解释或索要选择 |
| 用户明确要求检查详情 | 展开文件、证据、执行范围、未知项和修复状态 |

完整风险列表保留。最多突出三项是展示策略，不是扫描或永久隐藏范围。AI 判为疑似误报不自动删除原始发现；暂不修复和问题已解决保持不同状态。

## 任务级处理流程

```text
登记已授权开发任务和开始比较点
    → 正常开发，编辑 Hook 继续基础检查
    → 完成开发，冻结本次任务结束版本
    → 汇总整个任务的改动文件和 diff
    → 复用有效基础扫描，补未执行或过期部分
    → 收集有限关联上下文
    → 宿主 Agent 按快速 Skill 发现候选并检查反证
    → Runtime 校验范围、版本和证据，保存候选状态
    → 任务总结展示有用结果
```

快速核查包括没有静态告警的改动。静态工具提供确定的命中与执行证据，宿主 Agent 承担有限上下文推理，Runtime 管理任务身份、版本、预算、记录与修复边界。

### 任务开始比较点

登记任务时保存工作区、宿主会话、任务引用、开始版本、支持范围和用户需求中的相关功能约束。内部任务引用不显示给用户，也不是修改代码或修复漏洞的授权凭证。

比较点采用任务开始时的真实工作区，包括用户已有的未提交内容。不能只拿 Git HEAD 作为开始版本，否则会把此前改动算进本次任务。需要生成精确 diff 时，除哈希外还要有可验证的前像：首版对受支持源码使用有容量上限的本地临时快照，或在可用宿主事件中编辑前捕获目标文件。缺少前像则明确 diff 不完整。

前像、当前内容和文件清单分别管理，不保存真实凭据值到长期记录；环境文件、生成目录及链接的排除在任务范围中披露。大于预算的源文件保留未检查状态，不用静默截断制造完整覆盖。

任务结束时计算新增、修改和删除；重命名无充分依据时按删除加新增处理。同时有其他会话或外部程序修改时，记录范围冲突，不能把所有变化归给当前 Agent。首版优先支持单任务 Git 项目，状态锁只保护短事务，不能锁住整个开发过程。

### 复用基础检查

基础扫描覆盖本次任务完整改动清单，包含未跟踪的新文件和安全相关配置变化。保存实际执行的文件、规则、引擎、规则版本、数据日期和输入版本。

编辑 Hook 已执行的结果只有文件版本、所需规则和执行证明仍一致时可复用；缺失、延后、失败或过期部分在结束阶段补齐。一次任务中较早修改且没有告警的文件仍在任务范围内，不能只取最后一次 Hook 的范围。

源码文件没有改变时，不因为 Git 仍有其他旧暂存文件而反复扫描。依赖检查只在相关清单或锁文件变化时安排，并保留数据缺失和图不完整的限制。

### 有限关联上下文

以改动函数和敏感操作为起点，读取必要的调用方、被调用方、鉴权和校验函数、路由注册及相关配置。未修改但决定风险是否成立的文件可以纳入关联范围，记录它们的哈希和引用位置。

第一版复用现有安全读取、脱敏、哈希和分页约束，增加任务差异及上下文导航。词法引用和 import 仅用于定位线索；只有实际读取到的参数传递、条件判断或调用位置才能写进证据，不能伪装成完整调用图。

关键关联找不到、动态调用无法确定或预算不足时保留未知。不将整仓库无差别交给模型，不自动上传到另外的模型服务；宿主自身代码上下文出口按实际宿主和项目使用方式说明。

### 快速 Skill 的方法

新增一个面向任务结束核查的方法入口，不能把现有候选复核换个名字充当独立发现。首轮只覆盖有明确证据形状的检查：

| 检查方向 | 应读的上下文与证据 |
| --- | --- |
| 注入和动态执行 | 输入来源、参数传递、危险调用及有效约束 |
| 文件和网络访问 | 请求输入、路径或目标限制、校验位置与实际使用 |
| 身份与对象权限 | 当前用户如何传递，对象所属用户或租户在哪里核对 |
| 敏感数据返回 | 返回字段、序列化、访问条件及内部字段 |
| 新增依赖与配置 | 基础结果、实际版本归属、安全配置是否生效 |

第一遍从改动和敏感操作提出候选，第二遍对少量候选查找防护、反证和缺失环节。首版可由同一个宿主 Agent 分两步执行，不宣称独立多模型验证；更昂贵的独立复核在实测收益明确后增加。

模型分析只提供候选和静态依据，不执行源码中的指令，不凭严重度或置信度取得修复权限，不自动删除用户功能或修改测试来关闭问题。

当前 [triage_models](../../src/security_runtime/triage_models.py) 明确只验证已有发现，因此不能直接移除限制、把任意模型文字提交为原扫描器事实。[closeout](../../src/security_runtime/closeout.py) 目前恢复的范围也不能代替整个开发任务的开始到结束差异。

## 新增接口与结果契约

以下是拟议内部接口，当前没有实现，不要求用户记住名称或复制引用。

| 接口 | 作用 |
| --- | --- |
| begin_security_task | 已授权开发开始前登记任务和比较点 |
| finish_security_task | 冻结结束版本，计算完整任务差异，安排基础检查 |
| prepare_task_security_review | 返回当前任务的 diff、基础结果、上下文、预算及方法版本 |
| read_task_review_context | 按已绑定任务读取有限关联片段，并计入预算 |
| submit_task_security_review | 校验并保存结构化候选、反证、未知及核查完成范围 |
| get_task_security_review | 查看或恢复同一任务结果，供总结与按需查询 |

候选至少包含任务与结束版本、来源、风险类型、具体位置、条件性影响、证据引用、已有防护、反证、未知条件、建议修改及预期功能变化。证据引用绑定 Runtime 提供的片段和文件哈希，提交后源文件变化使旧结论失效。

原扫描器发现、任务级 Agent 候选、人工决定和执行验证分别保存。任务级候选可以关联同一个处理任务，但不伪造 scanner_sources、原规则身份或原扫描器验证通过状态。

首版任务级状态区分待核查、有静态依据、证据不足、反证排除和已处理。Runtime 接受记录只表示范围、版本和结构校验通过，不能称已经独立证实线上可利用。未覆盖的入口和业务条件仍显示未知。

规则内修复继续原扫描器复验；规则外修复必须重新核对对应静态路径，并在获准执行的环境中运行相关独立用例。没有相应规则或执行证据时，不能使用原规则复验通过的结论。修复后的语义重新核查与业务功能测试分别显示。

## 预算和不打断策略

预演可先采用以下起点：改动文件最多 20 个，直接关联文件最多 10 个，diff 最多 2000 行，交给 Agent 的累计上下文最多 64 KiB，每任务一个发现阶段和一个有限反证阶段。具体数值在预试验后固定，不作为质量或速度承诺。

文件、字节、读取次数、候选数、片段身份和过期时间可由 Runtime 强制限制。宿主 Agent 的推理时长和 Token 成本若无控制接口，只能观察和指导，不能宣称已硬限制。超过范围转为部分核查，允许用户按需继续，普通对话照常结束。

检查按任务结束版本去重。同一版本只核查一次；只读对话不改变任务代次或让旧结果失效。新源码变化才生成需要核查的新版本。失败、锁忙和已有未处理问题不能无限拉起聊天。

基础检查可在本地执行进程中保存结果，语义分析由当前宿主 Agent 在开发总结前按工作流完成。不能声称主 Agent 已结束后仍能在后台调用它；真正独立后台模型需要额外运行能力、数据出口和成本控制，不作为首版隐含能力。

Stop 仅做有界兜底：无有效开发任务时空返回；任务有待检部分时保存状态；不能把普通 MCP 调度 JSON 当用户提示打印，也不能不断以阻止结束来保证检查完成。明确用户批准的修复续办仍遵守其独立原范围。

## 开发顺序和验收

| 批次 | 开发内容 | 通过标准 |
| --- | --- | --- |
| 1 | 安静的结束事件与任务边界 | 连续普通问答不新增扫描、任务或提示；只读不污染代次；真实改动和未完成记录保留 |
| 2 | 开始比较点和全任务差异 | 多轮修改、新文件、删除及用户原有未提交改动分别正确；早期已扫描文件不从任务范围消失 |
| 3 | 基础结果与任务上下文包 | 静态命中、零命中、未改关联文件都能提供真实版本和范围，超预算保留缺口 |
| 4 | 快速方法与宿主编排 | Agent 按 begin/finish 核查，不要求用户再发继续；无告警敏感操作也进入核查 |
| 5 | 规则外候选与去重展示 | 有依据与未知分开，原始发现保留，普通聊天不重复已展示事项 |
| 6 | 选定修复及分层验证 | 原规则证明、语义重新核查和功能执行分别有真实证据，不改写测试或删除需求功能 |

首个端到端样例用三文件订单查询：入口接收当前用户和订单 ID，服务错误地丢掉用户身份，仓储只按 ID 查询，返回层没有所有权限制。静态工具可能没有告警，任务核查应找到身份传递断点和缺失控制，并说明上层防护未知。

配套安全对照把授权落实在实际访问之前；另设明确上层防护、只有 import 无调用、证据过期和关联文件缺失案例。危险与安全预期由独立样例判定固定，不能仅用 Runtime 自己的发现数评价效果。

首轮在 JS/TS、Python 和 Java 的有限路径分别验证：基础案例仍能检出，三文件风险可被解释，安全对照不会无依据报警，关键依赖未读取时保持未知。先做到有限范围可信，不承诺任意封装或完整跨库调用图。

上述任务接口与静默结束已落地；后续重点是真实宿主编排、危险与安全对照，以及独立的规则外风险修复复核。旧安装包须升级并重新连接，文档更新本身不改变驻留的旧进程。
