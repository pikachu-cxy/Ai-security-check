# 第 7 轮：有界数据流的增量分析与内存缓存

日期：2026-10-16。本轮在本地默认分支 `feature/runtime-mvp` 的第 6 轮候选上继续开发，保留此前未提交改动。核心静态规则包仍为 `1.3.2`，有界数据流包更新为 `1.5.0`；应用版本仍为 `0.3.4`。未提交、推送、构建安装包或重启其他会话。

## 已实现的范围

1. **解析缓存**：同一分析器实例内，按工作区、文件内容 SHA256、分析实现/解析器身份和语言复用 Java/Python AST。缓存树深复制，避免分支解释或调用方修改污染后续分析。
2. **分析结果缓存**：保存有界解释得到的原始问题、调用轨迹、源码哈希及解析查找记录，不保存用户授权、修复结论或可直接恢复的磁盘结果。复用后重新生成发现身份，不复用旧 normalizer 的工作区身份。
3. **内容与依赖失效**：复用前重新读取相关文件计算哈希；大小、mtime 一样也不能绕过。曾经不存在的模块/类文件也要核对，因此新增同名模块、SDK 遮蔽文件、删除依赖都会使旧结果失效。
4. **增量关联范围**：功能级 `feature` 扫描根据此前保留的批次关系，补入受改动文件影响的旧目标。当前按 80 文件批次保守扩展，不是逐函数的精确反向调用图。范围回执同时记录原请求文件和实际补入目标。
5. **全次一致性**：跨批次核对所有已读源码和解析查找记录，包含没有产生发现的文件；扫描期间变化则返回 PARTIAL，并清除该工作区及规则身份的结果缓存。阳性、阴性和缓存命中都遵守这一要求。
6. **软预算**：功能级分析 3 秒，项目级分析 30 秒；停止继续启动分析，未完成目标明确列入范围缺口。解析和文件版本核对不会被强制中断，所以不是严格墙钟上限。原有每批 256 上下文文件、8 MB、100 万解释步骤、调用深度 6 等限制保留。

缓存估算预算为 AST 32 MB、分析结果 8 MB，另限制 AST 条目 1024、结果批次 32；这是缓存计量上限，不是进程 RSS 保证。进程变化后清空继承的缓存和锁；不从磁盘读取 pickle 或其他可执行结果。

## 触发和体验边界

普通文件编辑 Hook、quick 模式仍不执行该数据流分析。新能力用于现有 `feature` / `release` 入口，没有将深查改成每次保存必跑。

本轮没有修改任务收尾的 quick 核查流程，没有新增后台扫描任务或自动调度。功能级入口现在具备增量复用能力；“任务完成后自动安排深查、跨进程连续编辑合并、后台进度与取消”等完整调度仍需单独接入和宿主验收。当前不声称这些已完成。

冷启动没有完整反向图，只能从请求目标及其可解析依赖开始；缓存被清理或批次被淘汰后，也不会凭空知道所有旧调用方。回执标记 `RETAINED_ANALYSES_ONLY`，完整程序覆盖始终为 false，不把未发现视为全项目安全或修复通过。

缓存生命周期属于同一分析器实例。连接内持有该实例的 MCP 服务能跨调用复用；独立 CLI 启动、重连或重启后需要重新预热。没有修改全局安装和连接配置；已有长期运行的进程需正常重载 Runtime 才能加载新实现。

## 同源性能对照

冻结优化前源码后，使用同一机器、同一固定源码、同一原生入口顺序运行。Java 772 文件、Python 428 文件与第 6 轮相同，只执行源码分析，不构建或运行目标应用。每组一次冷扫描、前版一次重复扫描、新版两次重复扫描；样本量不支持稳定时延承诺，也不包含 Semgrep、模型和宿主完整等待。

| 原生数据流范围 | 旧版冷扫描 | 旧版重复扫描 | 新版冷扫描 | 新版重复扫描两次 |
| --- | ---: | ---: | ---: | ---: |
| Java 772 文件 | 14.812 秒 | 15.235 秒 | 13.297 秒 | 4.703 / 4.578 秒 |
| Python 428 文件 | 1.906 秒 | 1.860 秒 | 1.672 秒 | 1.047 / 0.984 秒 |

本轮重复全量观察约减少 Java 69%、Python 44%–47% 的分析时间。冷扫描差异可能受系统文件缓存、负载和其他因素影响，不能据此保证首次扫描提速，也不能将这些数字直接和上轮不同条件的 21 秒相比。

为验证实际增量效果，只在私有副本追加注释，原始固定语料哈希不变：

| 修改与复测 | 实际分析目标 | 本次耗时 | 同范围无缓存对照 | 再次检查耗时 |
| --- | ---: | ---: | ---: | ---: |
| Java 改一个已分析文件 | 80 文件 | 1.484 秒 | 1.297 秒 | 0.532 秒 |
| Python 改一个已分析文件 | 80 文件 | 0.343 秒 | 0.344 秒 | 0.203 秒 |

增量结果与同范围无缓存结果一致。这里主要收益来自缩小扫描范围和重复结果复用；单次发生修改时不保证比同范围无缓存更快。私有副本首次全量预热仍花费 Java 27.407 秒、Python 5.938 秒，说明首次深查可能有明显等待，不能承诺所有项目均在 1–3 秒完成。
