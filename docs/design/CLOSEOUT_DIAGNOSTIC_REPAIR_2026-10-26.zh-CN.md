# Windows 收尾诊断与风险状态修复

本批针对 demo 验收暴露的三项缺陷。历史收尾仅保存 `TASK_EXECUTION_UNAVAILABLE`，没有异常详情，因此不能追溯认定其原因，更不能据 Hook 诊断库损坏推断收尾失败的因果关系。

## 实现

- 后台收尾在原签名队列行中保存执行阶段、固定异常类别、SQLite／系统错误码、Runtime 模块与函数行号。保留原 owner、任务版本、租约和取消代次校验；过期 worker 不能发布诊断。静态检查内部捕获的异常也保存在原结果，并通过任务结果接口返回。所有字段使用封闭结构，不保存异常文本、源码、局部变量、凭据或用户路径；诊断不是检查通过证明。旧失败缺少详情时明确返回 `NOT_RECORDED`。
- 原风险状态 `SCANNER_VERIFIED_RESOLVED` 纳入“已修复”投影，但仍要求非空复查哈希与当前所有相关文件逐一匹配。缺少证据、文件变化或不可读取时仍为待处理。原账本、复查事实和用户处置历史不重写。
- Hook 诊断历史仅为非权威观测，不是任务、基线、风险或扫描事实。只读查询从不修复数据库；新的实际 Hook 写入遇到 SQLite 明确的损坏错误时，或用户主动执行维护命令时，才尝试恢复。保留损坏原库，另存原始字节备份，初始化新日志并原子发布代次指针。旧进程仍持有原文件名，不能将其写入新日志。不会回放旧 Hook、扫描或伪造历史成功记录。
- 恢复要求自有普通文件、稳定文件身份、无符号链接／硬链接、无 WAL／journal sidecar，设置字节与代次上限。文件变化、锁忙、损坏指针、备份不一致或达到上限时保留原始资料并返回不可用；不清空任何权威存储。发布中断后沿同一备份与目标安全重试。
- 通用只读 SQLite 行查询复用 Windows URI 编码，支持同一诊断库的扩展路径；正常扫描范围与完整性规则不变。
- 扩大回归又定位到 Windows 二进制读取缺陷：原始文件描述符没有 `O_BINARY`，SQLite 文件头及签名密钥包含 `0x1A` 或 CRLF 时会被当作文本 EOF／换行处理。失败夹具 100 字节头实际只读出 27 字节。冻结上下文和严格快照 pin 现显式使用二进制模式，身份、签名、journal、sidecar、只读和长度校验全部保留。新增固定控制字节回归；原冻结字节测试改为显式 CRLF 字节输入并严格比对，不依赖平台文本写入的换行转换。

## 维护与验收

```powershell
.\.venv\Scripts\python.exe -m security_runtime.cli hooks repair-diagnostics --json
.\.venv\Scripts\python.exe -m security_runtime.cli hooks recent --path 'C:\path\to\project' --json
```

维护命令只操作固定用户目录中的非权威诊断历史。恢复后明确标记旧历史不可用及备份保留；不能据新库为空认定旧 Hook 未执行。

最新专项回归 93 项全部通过：新诊断与恢复用例、固定控制字节、风险处置、收尾原字节单次捕获和严格只读快照。最初扩大组为 118 通过、7 失败、1 跳过；其中两个风险流程的二进制读取失败在本批修复后通过。另一次源码恢复／单次捕获组为 52 通过、1 失败，失败为旧测试对 Windows 文本换行的假设，上述显式 CRLF 回归已通过。数字不跨重叠测试相加。

诊断兼容组另为 20 通过、5 失败；五个失败在独立的本轮修复前源码对照中逐一复现，四个保存返回为 `WORKSPACE_DEGRADED`，起因是产品比较基线使用尚未支持 Windows 的平台能力，第五个复合测试在相同启动护栏处未能进入预期的编辑扫描。未将该平台能力、整套回归或桌面验收标记为通过，也未为通过测试放宽扫描护栏。`pip check` 与 `git diff --check` 通过。

真实 demo 的旧失败任务仍是历史失败；新增诊断不能补造其原因、静态结果或正式源码复核结论，用户重测另行验收。此次 Windows 控制字节缺陷的确定性复现也不证明它就是历史 demo 失败的原因。本批开发沿原任务提交，未补建编辑后基线；原任务正式核查状态另据实际保存结果登记。
