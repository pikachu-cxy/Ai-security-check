# Cursor 自动接入：Hook 可行性探测

日期：2026-10-15。基线源码 `b9f0771`。本轮仅调研和测试传输机制，未打开生产适配的能力开关、安装新产品包或发布版本。

## 结论

在 **Windows x64 / Cursor 3.22.12 / Cursor Agents / This PC / 本地单项目** 的本次观察路径中，
原生编辑事件、编辑后 Agent 上下文回传、停止后的自动续执行均已取得真实桌面证据。
因此具备开发“日常编辑检查 → 任务结束统一提示 → 用户批准修复 → 安全复查”的宿主通道基础。
这不是完整产品接入验收，当前 Runtime 的保守能力声明暂不改变。

本次模型界面显示 Cursor Grok 4.6 Medium；不外推到其他模型、版本、IDE 入口、CLI、远程或多根工作区。

## 官方接口与实测结果

参考 [Cursor Hooks 官方文档](https://cursor.com/docs/hooks)（2026-10-15 查阅）。
以下区分文档能力、实测到达和本产品实现。

| 环节 | 本轮结果 | 证据与限制 |
| --- | --- | --- |
| 项目 Hook 发现 | 通过 | 隔离项目 `.cursor/hooks.json` 被真实客户端执行，未更改用户全局 Hook |
| `sessionStart` | 触发通过；上下文送达未确认 | 新会话真实触发；生成的 SESSION 标记未在回复中确认；同时存在用户级启动 Hook，不能据此认定客户端不支持 |
| `preToolUse` | 触发通过 | 观察到 Grep、Read、Write；本轮只返回 allow，未测试阻断、询问或输入改写 |
| `afterFileEdit` | 触发通过 | 原生 Write 修改合成文本后收到事件，文件留在项目内 |
| `postToolUse.additional_context` | 回传通过 | 第一组在 Grep 后注入随机标记，最终回复准确带回；另一次收紧为只在 Write 后注入，最终回复再次准确带回新标记 |
| `stop.followup_message` | 自动提交并回复通过 | 原任务结束后客户端自行提交测试消息，模型回复随机 STOP 标记及“本次没有用户修复授权，不修改代码。” |
| 有限续办与收敛 | 本案例通过 | 设置 loop_limit=1，并有按会话的本地一次性标记；后续人工新一轮编辑的 stop 即使 loop_count=0，也返回空对象，没有第二次自动提交 |
| `afterShellExecution` | 未运行 | 本轮禁止终端，只测原生编辑；旧回归不能替代本轮桌面 shell 验证 |
| 实际检查、批准修复、原规则复查 | 未运行 | 使用合成数字文本验证宿主机制，没有把标记当漏洞、修复授权或扫描证明 |

随机标记在 Hook 进程内临时生成，提示词不包含标记值。回执写在样例项目外；Agent 被要求不读取
Hook 配置、脚本或项目外文件。实际事件中没有 Shell 调用。观察到的标记回传支持传输结论，
不证明后续 Agent 一定执行安全工作流或遵守所有权限约束。

官方文档说明 `sessionStart` 不等待阻断结果，不能将它当作“首个编辑前基线已经完成”的保证。
各配置来源的返回值还会合并，因此重复安装、同名事件及多个上下文返回需要独立验收。

## 本轮发现的工作区差异

实际输入中的 `workspace_roots` 为单个相对路径，`CURSOR_PROJECT_DIR` 则与样例绝对路径一致。
最初两轮探测要求根路径为绝对形式，故未接受输入、没有返回标记；这些轮次不算消息回传失败。

最终探测依靠预先固定的项目参数与环境变量精确核对；相对根只作元数据，不与工作目录拼接，
也不用于访问文件或扩大权限。其他绝对根、多根和环境锚点不一致仍拒绝。
现有生产适配已区分相对根与绝对锚点，此次不修改其工作区安全逻辑。

## 下一步产品接入设计

1. 复用现有 Core、项目/会话绑定、任务基线及 MCP，不复制扫描或修复引擎。
2. 启动只建立会话并准备能力；首次实际修改前处理基线就绪竞态。普通聊天、只读调用不创建扫描任务。
3. 编辑及 shell 后根据真实文件变化登记检查；`postToolUse` 承担反馈传输，避免与专用事件重复扫描。
4. 日常编辑保持低打扰；任务结束有未完成核查时，使用一次受限 followup 让 Agent 通过现有 MCP 完成原任务核查并统一呈现。
5. 后续消息只要求检查和报告，不代表用户批准修复。用户选择具体风险后，仍通过现有授权与原规则复查流程；命令 Hook 不能自行制造或跨进程移用 MCP 修复凭据。
6. 以任务、内容版本和交付状态去重；取消、错误、超时、重连、旧结果、重复事件和多配置来源分别测试。不可只依赖客户端 loop_count。

下一阶段须完成真实风险反馈、用户拒绝/批准、逐项复查、恢复及累计等待验收，再逐项调整能力声明。
`sessionStart` 的上下文合并、shell 修改、慢基线、多个会话和宿主重启也保留为待验。
本轮不新增自动测试/构建、企业功能验证或未经批准修复。
