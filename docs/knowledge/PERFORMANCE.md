## 测量边界

- 扫描结果的 execution.timing.scan_ms 覆盖 Runtime 至结果发布；duration_ms 只到最终收尾之前，不能混用。
- scanner_runs 各引擎并行执行，不能相加作为用户等待。scan_stages_ms 中 target_preparation 包含规则解析和输入捕获，阶段也不能直接求和。
- 宿主日志 McpToolCall.duration 是宿主观测的工具调用耗时，包含调用链开销，不等于服务端函数 CPU 时间。
- 首次证据读取至提交保存为复核区间，包含模型、宿主、工具和其他工作；不是纯模型推理时间。业务审计关闭表示未执行，不应列成耗时为零的已完成审计。
- 已实现 performance_trace.py 和 scripts/performance/report.py：可选本地计时、队列事件、复核事件和 MCP 区间合并。既有未开启的细分事件不能事后恢复。纯模型耗时和每阶段 token 仍需要宿主额外观测。

## 优先优化

1. **先减少宿主往返与冗余返回。** 接口已支持 get_development_risks(limit=20, include_history=false)。此样本的 16 条候选可从提交前后各四页降到各一页；仍须提交成功后从 offset=0 读至 next_offset 为空。历史仅有需要时加载。减少六次调用的收益待同输入复测，不能承诺省去整个 52.940 秒。
2. **合并证据阅读与复核。** 同文件相关窗口按需合并，复用当前版本的实际 evidence_ref；保留候选逐项判断。当前已一次提交 16 条，无需拆成 16 次。证据读取会保存引用，不能未经并发一致性验证就批量并发写同一记录。
3. **测量 OpenGrep 固定成本。** 两个样本均由 OpenGrep 主导；拆出进程启动、规则装载、解析与匹配，再决定缓存优化。扫描器已有并行执行，重复并行化没有证据收益。不得靠删规则或排除正式文件宣称优化。
4. **补齐收尾差额。** 使用已有 queue_event 和 check/scan/MCP spans 测量排队、工作进程启动及返回唤醒；只对证实的瓶颈改动，保持输入一致性验证与失败诊断。
5. **同构建同输入复测。** 区分冷/热缓存，保留全部样本与失败；累计至少 20 个样本再报告样本 P95。业务审计默认关闭保持不变，不能用删掉必要候选复核换取速度。

早期账本分页方案的测量口径：风险列表默认每页 20 条、摘要去掉 assessment 的重复 finding/source_hashes、提交仅返回保存回执、证据窗口批量读取和重复窗口去重。完整详情可显式读取，提交后仍从头读齐所有风险与处置。按 16 候选/10 窗口的历史流程，调用结构由 8+10+1=19 次降为 2+1+1=4 次；这是调用数分析，不是已证明的端到端耗时或 token 降幅。安装生效须核对实际构建。

知识库索引生成器只在内容变化时写入，避免无变化的索引被监听再次记录。仅更新文档仍可能正常需要收尾；应在所有写入后、最终回复前完成检查，不能以禁用 Stop 掩盖未完成复核。Stop 对新版本的兜底与同版本失败反复续接是不同问题。

## 当前耗时优化顺序

原生安装包隔离样例的实测：收尾 10.703 秒包含扫描至发布 10.047 秒；首次证据至复核保存 8.423 秒包含 Agent/脚本交接与工具时间，不能作为纯模型推理时间。20 组交替读取中，10 窗口逐个读取中位 191 毫秒、批量 134 毫秒；10 风险两页读取 23.7 毫秒、一页 11.9 毫秒。样本为直连 stdio，不代表 Codex 桌面端到端时间。

1. 统一结果原子保存并随收尾返回首批发现，消除就绪空列表窗口和一次列表往返。当前重构已通过原生包隔离验证：10 个候选随收尾一次返回，批量取证、复核保存与最终读取完成，没有提交前额外读取列表。
2. 降低宿主读取量和交接轮次：复用统一结果第一页、批量证据、按需完整字段，观察桌面调用间隔；不能把 8.423 秒全算成可优化模型时间。
3. 扫描组件准备：版本探测样例单次达 2.3–5.0 秒、规则配置准备达 2.36 秒；优先定位重复探测和缓存身份条件。各计时有嵌套/并行，不能相加。
4. 证据持久化：单文件读取中位约 0.9 毫秒，证据保存约 9 毫秒。统一对象基础上评估批量单事务，保持证据哈希、路径与版本校验；此优化尚未实现。
5. 扫描器真正执行：按真实规则解析/匹配耗时定位，不删规则、不降低覆盖。单次扫描样例不能推导 P95；需同构建同输入冷/热样本。

统一对象可能增加单次签名记录的读写体积，必须实测，不能仅凭存储简化承诺耗时下降。

统一对象原生包的单次隔离验证：收尾返回 9.858 秒、10 窗口批量证据读取 0.459 秒、复核保存 0.138 秒、最终列表读取 0.028 秒。之后两组读取样本中，批量证据约 0.48–0.50 秒，逐个读取合计约 0.65–0.75 秒。统一对象增加了证据逐项保存时的序列化成本；下一步应优先把批量证据保存合并为单事务，而不是声称本次重构已降低所有阶段耗时。样本未达到 20 组，不报告 P95，也不推导桌面端到端或 token 降幅。

### 普通开发的说明读取与候选复核

原生 Codex 的干净任务由编辑与 Stop Hook 驱动。真实 Codex 样例已在 Agent 零次读取产品 Skill、零次主动调用安全 MCP 的情况下保存本轮扫描。专项方法仅在需要时加载。仅替换 MCP 服务仍可能命中用户目录中的旧 Skill，验收时应分别核对实际读取路径和运行构建。

隔离的 Codex Hook/MCP 场景中，单个 SQL 注入和固定命令误报均由一次待办与证据读取、一次复核提交完成；提交直接返回已保存的风险页。多页或证据不足时仍需继续读取。规则包在计算内容摘要时一并统计规则字节数；全局路由在校验与首次接入期间可复用同一次操作内验证过的包内容。调用次数与扫描用时分开计量。
