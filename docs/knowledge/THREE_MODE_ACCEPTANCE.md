## 修复前结论

2026-11-08 在重启后的本机 Codex 验收已安装 0.3.13，构建 `9d51190087c8946b2464099d8259bb64108aea5315e8a5c5a1333b10c7ca17df`。三种配置各四项，共 12 个真实开发回合全部结束，四个业务审计子任务也已结束。验收未通过：静态扫描和静态复核可落盘，但报告交接及业务审计领取存在阻断问题。本轮未修改产品实现、安装或推送，未补扫、代交审计结论或修复验收样例来消除告警。

## 发现的问题及证据

### P1 业务审计缺少可执行的交接参数

四个父任务都执行 stream_prepare、实际创建子 Agent、stream_started。子 Agent 的 claim 请求均缺少必填 check_ref、agent_ref。接口声明要求这些字段，prepare 返回状态和令牌但没有完整可复制调用包；合并 MCP 的通用错误把参数校验失败折叠为 DEVELOPMENT_CHECK_REQUEST_INVALID。子任务因此连领取都未完成，未形成审计证据或直接保存记录。四轮待审路径分别为 2、3、2、2；权限对照也未审。这是流程漏执行，不是已完成审计后的模型漏判。

定位：`mcp_tools/development_check.py::process_development_audit`、`audit_stream_service.py::manage`、`global_mcp.py` 的开发请求校验分支，以及开发指导。应由产品在绑定执行者后生成包含 workspace_path、check_ref、agent_ref 和任务令牌的完整调用包；缺字段返回字段级可恢复错误。只读子任务可直接提交的底层能力，本轮尚未验证成功。

### P1 零候选先交付未完成却未及时补交

A/B CLEAN 的首次 Stop 仅耗时 2.342/3.295 秒便返回未完成，远未达到当前等待模式的上限；读取时状态为 QUEUED。扫描最终分别在主回合结束后约 4/7 秒保存，0 候选且无扫描或监听缺口。随后没有新的最终报告替换旧的未完成提示。不能把这两轮算作扫描失败，也不能因为后台最终成功便把用户体验判为通过。

可确认的是原生 Stop 提前走了 INCOMPLETE 交接，晚到的零候选结果未在该回合补交。具体触发提前退出的瞬时状态未保存在当前诊断中，不能断言是 18 秒预算、网络或监听中断。下一步围绕 `development_stop.py::native_closeout`、`saved_handoff`、`development_check.py::projection/wait_saved` 的当前批次与旧 worker 租约投影补齐诊断，复用已有结果，不能用重扫修正。

### P1 历史误报状态抑制新批次静态报告

A ALLOWLIST 扫描保存一条 SQL 候选，复核关闭，聊天却仅交付开发结果，没有候选说明和风险链接。本批 dirty_seq=2，但风险仍沿用旧 seq=1 的 DISMISSED 判断，用户处置为 ACTIVE。源码 import_scanner 复用风险对象时只追加新观察，不重置当前判断；get 的 reminder_suppressed 又直接使用风险对象的旧 DISMISSED，Stop 据此静默。

本例代码本来有严格白名单，因此不是已证实漏报真实漏洞；缺陷是旧批次的 Agent 误报结论被当作新批次有效抑制条件。应将当前批次判断与历史判断分开投影；只有当前有效复核或明确用户处置可以抑制新批次报告。历史记录继续保留。

### P1 审计未完成时完整静态报告丢失

C MIXED 的 SQL 复核已保存，但由于业务路径待审，提交只返回待办回执和下一步读取，未返回 report_text。父 Agent 最终只说“确认 1 项、4 项待确认”，缺少具体位置、问题、影响及建议。A/B MIXED 则能交付完整中文报告与链接。应由产品分别表达静态报告已可交付、业务审计仍待完成，生成稳定完整报告，不能让尚未完成的一项挡住已经保存的漏洞详情。

### P2 审计结束与主聊天结束没有可靠衔接

C CLEAN、MIXED、LOGIC 主回合结束时子 Agent 仍在执行，随后子任务才报告领取失败。C ALLOWLIST 等到了子任务失败，但主回复仍不能完成安全交付。四项的审计启动都晚于本轮源文件编辑，不能证明审计与开发实际重叠或持续消费后续修改。两个订单文件已进入待审集合，但 claim 为零，所以流式覆盖与结果保存验收未通过。

Stop 已冻结输入不等于子 Agent 审计已完成。应绑定本轮审计任务状态，保存领取失败和可恢复原因；晚到结果依原任务补交，避免同一批次重复扫描或提交。不建议通过固定延长所有 Stop 等待掩盖交接失败。

### P2 回复质量与重复展示

MIXED 每轮有 5 条扫描候选：SQL 一条、依赖一条、同一演示凭据的三条规则命中。三条凭据卡片不是重复提交；但用户层面重复展示，应按证据关联展示来源。部分规则落入“潜在安全风险／尚无对应中文规则解释”的通用文案，依赖修复建议也不够具体。B/C 对依赖利用条件和凭据真实性保留待确认是合理区分，不能要求对本地演示值做真实凭据验证。

日志中 9 轮各有两个 final_answer 片段（开发答复后 Stop 续接安全答复），3 轮只有一个；这不等于重复保存，但说明“一次统一最终交付”的体验仍未达到。需要用户检查桌面实际呈现是否合并。原始回复已在原聊天保留。

## 修复优先级与性能约束

1. 先修审计完整交接包和字段级校验反馈，避免四个任务全部无效等待；在领取、直接保存、增量文件覆盖、主任务提前结束四个边界回归。
2. 修复旧判断对当前批次投影的污染，以及未完成审计吞掉已保存静态报告的问题；只改状态投影和报告，不新增扫描。
3. 对零候选提前退出补最少必要的原状态诊断，并用保存结果完成补交；保持同一批次单次扫描和幂等提交。
4. 正确性通过后再精简审计管理调用和重复卡片。模型首次输出等待与产品本地耗时分别统计，不用改扫描超时掩盖模型启动延迟。

本轮不宣称修复完成。真实端到端缺陷应优先于新增功能；不以单元测试通过替代真实宿主闭环。完整相对指标见 [样本](THREE_MODE_ACCEPTANCE_SAMPLES.json)，包含各扫描阶段、调用数、输出 token 和等待区间；无逐次模型流首末片段遥测的区间保持未知。
