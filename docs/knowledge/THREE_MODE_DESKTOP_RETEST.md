# 重启后复用 Codex 既有聊天验收

日期：2026-11-08。已安装版本 0.3.13，构建 `0370c199365fdde11bd0f48107cd9a2ae15e3d155f17cacf3e8d4f8bd2178475`。在真实桌面已有聊天执行三种配置各五种场景，共 15 回合；不是用 CLI 隔离新会话代替桌面验收。

## 结论

静态扫描与静态复核的本轮检查项通过；业务审计续接和最终报告一致性未通过。12 个开发回合各保存 1 次扫描，3 个只读回合均未扫描；4 次静态复核提交全部首次保存，无重复提交或证据补读。4 个业务审计场景中，仅混合漏洞场景完成直接保存；其余 3 个没有完成领取。订单权限对照因此未审出，属于流程漏执行，不能归结为模型已审但漏判。

本次仅执行验收和读取保存记录，未补扫、未代交审计判断、未修改产品实现或安装。三个项目的验收修改保留；产品设置已逐字节恢复为验收前文件：复核开启、业务审计关闭。

## 场景与人工查看

复用 zero、real_sql1、allowlist1 三个已有项目及四个原聊天。每组先在不同项目并行执行 CLEAN、MIXED、ALLOWLIST；同一 zero 项目的 LOGIC 在 CLEAN 完成后执行，READONLY 在 ALLOWLIST 完成后执行。组间依次切换，避免配置混淆。

A＝仅静态扫描；B＝静态扫描＋复核；C＝静态扫描＋复核＋业务审计。所有组保持原扫描器、规则、等待模式及 64 KiB 响应预算。C 组实际走的是已有审计执行者续接分支。

| 场景 | 开发任务 | 验证重点 |
| --- | --- | --- |
| CLEAN | 归一化函数内部重命名，增加空白／重复／顺序测试 | 无风险重构及零候选收尾 |
| MIXED | 查询参数兼容性修改、依赖清单注释、演示凭据变量改名 | SQL、依赖、凭据三类扫描与复核 |
| ALLOWLIST | 白名单查询参数改名，同步拒绝输入测试 | 历史误报不污染当前扫描，复核能排除误报 |
| LOGIC | 依次新增订单查询和摘要两个模块，保留安全与旧兼容路径 | 增量文件覆盖、权限逻辑审计及跨文件调用 |
| READONLY | 解释白名单与参数绑定差异 | 无编辑不扫描，不重复旧报告 |

原始提示词及逐轮回复保留在本地验收产物和既有聊天，本页仅记录去标识结论。结构化指标见 [桌面复测样本](THREE_MODE_DESKTOP_RETEST_SAMPLES.json)。

## 发现的问题及优先级

### P1：重启后复用旧审计执行者的交接没有闭环

四个场景的 stream_prepare 都返回 executor_bound=true、FOLLOWUP_EXISTING_EXECUTOR，但不返回新的完整 child_call。父任务随后只唤醒原执行者。CLEAN 和 LOGIC 的子任务缺 check_ref、action、agent_ref，得到字段级 INPUT_INVALID；ALLOWLIST 没有调用领取，直接报告缺交接包。不是子 Agent 消失：这些旧执行者实际可被唤醒，缺的是可执行的完整交接。混合场景依靠已有上下文完成，说明成功取决于聊天旧上下文，不够确定。

源码原因：audit_stream_service.manage 的 prepare 分支仅在新建／撤销／rotate 时生成令牌；绑定已存在时只返回 _status。child_call 仅在 started 且有令牌时返回。此前修复覆盖首次注册，但这次桌面复用路径没有覆盖。优先让已有执行者恢复也获得完整、当前有效的调用包；若旧能力不可恢复，则在产品确认没有活动领取后按原任务安全换发，避免让模型猜身份。不得仅继续返回“请跟进旧执行者”。

### P1：审计结果在报告生成后保存，最终回复没有刷新

C-MIXED 的静态复核回执先生成“业务审计进行中”的报告。13.831 秒后，审计提交返回 applied=true，当前三条路径均已接受且进度 COMPLETE。再过 8.133 秒，主聊天仍输出旧报告；最终 Stop 允许结束。台账已完成，用户看到的状态却未完成。

development_stop.native_closeout/report_notice 以 dirty_seq＋scan_id 标记报告／复核提醒，已经提示过同一批次时直接去重；标记没有包含审计结果更新。建议在现有最终交付路径使用审计／报告内容修订号，已有新结果直接补入；不能依靠用户下一次输入，也不应增加正常无审计回合的轮询或扫描。

### P1：晚到审计发现绕过已完成静态复核的重复关联

C-MIXED 台账将同一 sample.py SQL 拼接保存为两条 CONFIRMED：静态告警行 4 与审计发现行 3–4。这是不同来源的两个发现，不是同一个提交重试。首次读取候选时业务审计尚未保存，所以 related_confirmed 还不能提供该项；仅在首次取证时提示去重无法覆盖晚到结果。应在审计结果汇入／最终报告归并时按证据和位置关联同一问题，保留两份来源和原始记录，不增加模型补读。

### P2：文案、位置与交付形态

所有对用户展示的漏洞标题和问题为中文，但 MIXED 中仍有“潜在安全风险／尚无对应中文规则解释”的兜底说明。凭据同一行存在多条规则卡片；这些尚未确认的演示凭据不能当作已验证可用密钥，也不能通过外部验证来补证。依赖实际在 requirements.txt 第 2 行，扫描器位置是第 1 行；A 组报告有 PyYAML、CVE 和修复版本，B/C 复核后模板却丢掉这些具体字段。建议保留结构化依赖信息，明确扫描器位置与实际依赖行的区别。

本轮 8 个回合各有两个 final_answer 片段（先开发回复，Stop 后安全回复），7 个只有一个；没有两次完整安全报告重复保存，但“开发回复＋安全回复”的双片段体验仍存在。原始片段全部保留供人工查看。

## 性能判断

12 次扫描为 4.646–11.347 秒，中位数 8.508 秒。第一组四个开发聊天初始输出等待为 117.736–118.611 秒；后续热回合约 2–4 秒。没有请求发出／模型首片段网络遥测，不能把 118 秒进一步归因到具体网络或服务端阶段。

B-CLEAN 的 Stop 为 23.120 秒，而产品扫描为 8.666 秒。进一步按保存的 scan_context 时点拆分：Stop 接收至 scan_context.started_at 为 14.832 秒，随后上下文区间 7.240 秒，结束后 1.048 秒。前一段包含任务准备／调度及部分扫描准备，不能直接称为排队时间；当前诊断不足以把它分到具体锁或启动步骤。此长尾应单独排查，不能据本次样本声称 Stop 性能完全通过。

静态复核本地写入完成约 0.390–0.916 秒；证据返回到首次提交为 7.485–17.185 秒。优先解决审计交接与报告一致性，再定位 Stop 扫描前的长尾；模型组织提交的时间与本地落盘时间分开优化。

## 验收边界

本轮覆盖已有小型项目和已有聊天重启续接，不代表大项目、多 worktree、网络断连、依赖实际安装或所有宿主都通过。LOGIC 的权限对照按给定业务约束应被审计评估，C 组尚未领取成功，不能以零扫描候选宣称无权限漏洞。全部扫描保存范围 FULL、扫描 gaps 为空；这只证明本轮记录文件的静态检查完成，不替代未执行的业务审计。

此前隔离 CLI 新会话的修复验收与本次桌面旧聊天续接属于不同路径；保留两者结果，当前桌面续接缺陷仍待修复。未改实现、未额外增加扫描或模型复核调用来掩盖问题。
