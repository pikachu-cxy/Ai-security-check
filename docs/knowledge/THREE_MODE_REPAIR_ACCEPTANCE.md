# 三种配置交接修复验收

## 当前实现与验收范围

修复覆盖：排队任务误用旧租约、旧误报抑制新批次、业务审计完整交接、静态报告与审计待办分离。真实验收进一步发现并修复零候选回复预告、跨来源重复报告以及嵌套提交字段错误不明确。没有改变扫描器、规则选择、扫描等待预算或正常 Hook 数量，没有新增后台扫描队列或常驻服务。

本机使用既有验收项目、隔离 Codex CLI 配置和真实模型运行；正式产品配置未改。CLI 运行与桌面已有聊天不同，原始回复保存为本机验收交付物，不能声称已在桌面已有聊天中执行。静态扫描和业务审计都由原生流程触发，不用补扫或代交结果修正验收。

## 中间失败及边界

- 首轮 A/B 零候选扫描均完成，但回复自行预告“安全报告待返回”。已修正会话入口及内部指导，A2 CLEAN 与 C CLEAN 只交付开发结果，不留下待返回尾注。没有增加零候选 MCP 调用。
- C MIXED 曾把业务与静态 SQL 分列。首次复核响应现在附当前已保存同文件审计摘要，原提交可关联；C3 已验证一项 SQL。
- C2 LOGIC 的第一次提交参数无效，修正后第二次成功；不计为首次保存通过。C3 LOGIC 首次保存成功。
- C2 MIXED 子任务遗漏 Observation 字段并多传 kind，两次失败，未保存业务审计。产品仍保留完整静态报告和独立审计失败状态；此样本不算审计通过。修复后首次 claim 附模型定义生成的必填字段，嵌套错误返回具体路径及允许字段；C3 首次提交成功。
- 演示凭据未外部验证；模型确认的是源码中令牌格式硬编码，不能把报告的 Agent 已确认理解为已验证令牌有效。依赖仅确认受影响版本声明，未安装依赖验证运行时可利用性。
- Trivy 的依赖定位仍使用扫描器文件首行，实际声明在第二行；真实回复指出了差异。本次未改扫描器位置适配，列为后续展示改进项。
- 订单两文件实际在首次领取前均已入队，三轮均覆盖两文件；“领取后再新增文件”的消费、旧版本/部分结果保存与再领取由增量服务回归覆盖，不冒称这三轮模型记录已经展示了两个领取批次。
