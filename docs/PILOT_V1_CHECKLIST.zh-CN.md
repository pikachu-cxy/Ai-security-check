# 第一版受邀试用开发清单

更新日期：2026-10-12。

第一版面向有开发经验、但不熟悉安全的程序员，在现有 AI 编程工具中完成检查、核查、选择问题、批准修复和验证。试用要验证用户能否独立判断下一步，并理解修复结果。首轮以 5 人、1 至 2 周为目标，先支持 Windows、Codex、Git 项目和一种经过验收的主要技术栈。

P0 是邀请用户独立试用前必须完成的开发或验收；P1 可以在首轮反馈后补齐；P2 随扩大用户范围推进。首轮支持范围比公开个人免费版发行范围更窄，其他语言和框架的已有结果仍按实际覆盖展示。

当前工作树的源码版本为 0.3.2，包含未提交的新模块。旧文档和不同构建的验收不能直接作为该版本通过的依据。下列任务均未标记完成；源码存在、测试用例存在、原生包通过和真实桌面通过分别记录。

## 当前基础和实际缺口

| 环节 | 已有基础 | 首轮还缺什么 |
| --- | --- | --- |
| 接入 | 统一安装、固定启动器、组件准备、失败重试和本地升级恢复 | 同一最终候选的无缓存联网安装与真实桌面全过程验收 |
| 结果组织 | 依赖归并、最多 3 个推荐任务、证据和上下文失效 | 项目具体影响、排序原因、当前状态与历史记录一致 |
| 风险核查 | 原始扫描与 AI 复核分开，独立质量记录 | 普通聊天里的人工决定、反证、暂缓与恢复入口 |
| 修复 | 选定任务授权、宿主修改、原扫描器复验 | 最小修改与业务行为说明、审查和撤销步骤的统一体验 |
| 风险关闭 | 新增密钥覆盖证明、持久关闭和任务收尾补查 | 最终候选的自动触发、补查、重连和提示送达验收 |
| 功能验证 | 通用执行接口、独立功能结果、专项算术前后回归 | 首轮修复路径的前后对照，以及一致的用户结果表达 |

密钥移除后的关闭机制已有 [RiskClosureService](../src/security_runtime/risk_closure.py)、[CloseoutService](../src/security_runtime/closeout.py) 和对应回归。已有原生手动复验记录不能代替最新包的真实桌面自动验收。通用功能结果仍保留未知的修复前基线；[算术回归](../src/security_runtime/arithmetic_regression.py) 已提供一个有限场景的前后对照，不能推广为任意业务兼容性证明。

### 01 固定试用范围和候选版本

**当前基础：**已有版本槽、构建身份、包清单与完整性校验。当前目录同时存在不同修订的源码、包和验收记录。

- [ ] 登记首轮支持的主要语言、框架或 API、依赖清单和项目规模。优先选择已有独立样例和真实规则执行依据的路径；项目含未支持文件时，分别展示可检查范围和缺口。
- [ ] 全部 P0 修改完成后，冻结唯一源码状态，构建对应原生包，记录版本、构建身份、源修订、未提交标志和包摘要。源码、包内模块、规则、配套 Skill 与说明一致。
- [ ] 在这份候选上完成所需回归、包完整性检查、真实引擎复验及 02、03 的验收。曾失败或中断的检查必须有该候选的最终结果；构建成功不能代替验收。

**完成标准：**发给所有试用者的是可识别的同一候选；能从反馈定位到实际源码和包。公开 Release、包管理器发布和远程自动更新不作为受邀试用门槛。

**入口：**[打包](../scripts/build_standalone.py)、[原生包验收](../scripts/verify_artifact.py)、[构建身份回归](../tests/test_build_identity.py)。

### 02 新机器安装和失败恢复

**当前基础：**统一安装已区分配置完成与检查就绪，支持准备组件、有效缓存复用、离线核验和失败重试。已有缓存条件下的隔离通过记录不能证明首次联网准备。

- [ ] 在无产品缓存的 Windows 环境，以最终候选完成真实下载、安装、重启和首个实际检查。无需开发 Python 环境。
- [ ] 验证断网或下载中断、已有过期数据、无缓存离线，以及首批实际使用的代理配置。失败明确显示未就绪，保留配置和可用旧数据；同一入口重试能恢复。
- [ ] 在说明中提供漏洞数据过期后的手动刷新或重跑安装步骤，并验证恢复。数据日期在结果中可见；后台定期更新可后做。

**完成标准：**新人按说明能得到真实结果；发生准备失败时能知道检查尚未完成，并恢复继续使用。保留用户原有配置和自定义 Skill。

**入口：**[个人安装](../src/security_runtime/personal_install.py)、[就绪核验](../src/security_runtime/install_readiness.py)、[就绪回归](../tests/test_personal_install_readiness.py)、[进度传递回归](../tests/test_install_stage_transport.py)、[安装验收](../scripts/personal_install_acceptance.py)。

### 03 真实桌面自动检查和收尾

**当前基础：**MCP、Hook、工作区绑定、首次发现归属和任务收尾代码已存在。收尾持久化、逐规则凭据关闭、并发新事件、延后检查和只读复用已有回归；此前冻结 MCP 重连断点已修复并在独立原生包复测。最新候选仍须完成真实桌面自动触发验收，手动 MCP 通过不能替代。当前结果见 [本批交付状态](RUNTIME_CLOSEOUT_CHECK.zh-CN.md)。

- [ ] 复验收尾完成、重连后复用、新改动使旧结果失效，以及失败保留待检查意图。修正仍可复现的失败。
- [ ] 最终候选安装并完全重启宿主、审核 Hook 信任后，在独立演示 Git 项目中实际编辑：首次检查、多文件修改、普通自动提示、选定问题修复、原规则复查和任务结束补查。
- [ ] 验证只读与无变化跳过、已有风险不误称本次新增、忽略保留风险、重连续办，以及修改期间出现新事件。整库请求执行整库检查，继续已选任务不重复扫描全仓。

**完成标准：**真实聊天中看得到正确提示，用户不需要搬运内部引用或工具调用顺序。手动 MCP 和模拟事件分别记录，不作为桌面自动触发通过。

**入口：**[全局 MCP](../src/security_runtime/global_mcp.py)、[宿主 Hook](../src/security_runtime/codex_mcp_hook.py)、[收尾服务](../src/security_runtime/closeout.py)、[收尾回归](../tests/test_closeout_regression.py)、[原生收尾验收](../scripts/closeout_mcp_acceptance.py)、[原生接线回归](../tests/test_native_global_hook_wiring.py)。

### 04 当前处理状态和历史展示一致

**当前基础：**summary 已排除确认关闭的凭据推荐项，历史扫描保留。任务总数和复核统计仍主要来自历史扫描；中文 summary 尚未完整展示当前关闭事实。

- [ ] 分开展示当前待处理、等待复查、已确认关闭、暂缓，以及历史扫描中的原始数量。让聊天、紧凑汇总和完整详情使用一致的状态投影。
- [ ] 相关代码、规则或所需证明变化时使旧结论失效。保留原始发现，不通过删除历史来降低数量。
- [ ] 密钥候选移除并复验后，说明代码中的候选已关闭；已暴露凭据是否轮换或停用另列待确认。单项关闭不能改变其他能力的部分覆盖。

**完成标准：**演示候选从发现到关闭、重连、再次修改后，各入口状态一致；缺失引擎、超时、未执行、部分覆盖与无发现不会混淆。关闭证明当前以已有支持路径为限。

**入口：**[汇总](../src/security_runtime/security_summary.py)、[中文输出](../src/security_runtime/human.py)、[关闭事实](../src/security_runtime/risk_closure.py)、[密钥覆盖回归](../tests/test_secret_recheck_coverage.py)、[无发现回归](../tests/test_no_findings.py)、[汇总回归](../tests/test_security_summary.py)。

### 05 具体风险解释和优先级排序

**当前基础：**最多 3 个推荐任务、依赖归并、AI 原因和未知条件已有。通用代码说明仍较笼统；当前排序先考虑是否可处理，再考虑主题和严重度。

- [ ] 对首轮支持的风险，选中后给出具体位置、输入来源、危险操作、现有防护、触发条件、可能影响、最小修复和行为变化。扫描事实、AI 推断和未知条件分开表述，并保留依据位置。
- [ ] 推荐项说明为什么排在前面。结合影响程度、复核依据和已知暴露条件排序；证据不足的高影响候选在概况中可见，不能因尚未核查而被埋没。
- [ ] 紧凑结果保留关键解释，完整发现可继续查看。多个扫描器命中不能直接作为漏洞成立或可利用的证明；代码变化使旧解释过期。

**完成标准：**真实命中、明确反证和证据不足三类样例中，不熟安全的开发者能说出风险条件、可能影响、下一步及未知项，无需逐条口头解释。

**入口：**[任务解释与排序](../src/security_runtime/security_summary.py)、[Hook 说明](../src/security_runtime/hook_user_feedback.py)、[复核记录](../src/security_runtime/triage.py)、[汇总回归](../tests/test_security_summary.py)、[用户反馈回归](../tests/test_hook_user_feedback.py)。

### 06 最小人工核查和暂缓入口

**当前基础：**独立质量记录已有确认问题、误报、需要上下文、接受风险等状态；主要通过质量脚本处理。当前忽略表示拒绝本次修复，不表示误报或风险消失。

- [ ] 在现有聊天中，针对选定问题提供确认、补充反证、证据不足、暂不修及原因的入口。用户决定与 AI 复核分开保存。
- [ ] 可以查询决定、恢复待处理，并在重开聊天后续办。决定绑定当前项目、问题和证据范围，不能串到其他问题；相关代码或规则变化时要求重审。
- [ ] 首轮如减少暂缓事项的重复提示，只在用户明确决定的当前范围内生效，完整列表和暂缓数量仍可见。AI 疑似误报不自动永久隐藏。

**完成标准：**用户能从当前任务完成一次人工决定、恢复和续办；原始发现保留。复杂到期策略、跨扫描自动迁移和批量抑制留在 P1。

**入口：**[质量记录](../src/security_runtime/finding_quality.py)、[存储](../src/security_runtime/storage.py)、[MCP 入口](../src/security_runtime/mcp_server.py)、[质量回归](../tests/test_finding_quality.py)、[任务复核回归](../tests/test_task_triage.py)。

### 07 首轮依赖升级建议

**当前基础：**依赖任务按组件归并；OSV 已保留修复版本，Maven 有有限的本地声明归属和逐公告升级选项。Trivy 主路径尚未保留上游 FixedVersion；其他生态的修改位置需按首轮范围补齐。

- [ ] 主、备用引擎统一保留包名、实际解析或声明版本的区别、公告来源、受影响范围、修复选项和数据日期。上游没有给出的信息保持未知。
- [ ] 对首轮依赖清单定位直接依赖的实际修改文件和字段。传递依赖有引入证据时说明升级哪个直接组件；引入来源不清楚时显示需要补充解析。
- [ ] 同组件多个公告合并成一个处理任务，分别保留修复选项与复查结果。没有联合版本依据时不猜共同升级目标；跨主要版本的兼容变化另列检查事项。

**完成标准：**首轮至少一个直接依赖案例能回答当前版本、改哪里、升级依据和复查办法；传递依赖与缺证据案例说明下一步。试用项目不包含某生态时，不要求先补齐该生态的完整解析。

**入口：**[主扫描适配](../src/security_runtime/scanners.py)、[OSV 适配](../src/security_runtime/osv.py)、[依赖上下文](../src/security_runtime/dependency_context.py)、[依赖运行回归](../tests/test_dependency_scan_runtime.py)、[回退回归](../tests/test_dependency_fallback.py)。增加首轮清单版本归属与逐公告升级选项的小型针对性样例。

### 08 最小修复和差异审查

**当前基础：**选定任务授权、修复计划、宿主编辑和原扫描器复验已有。修复质量与审查体验仍需在真实聊天中确认。

- [ ] 修改前说明必要的业务条件、预计行为变化、允许修改范围和验证计划。保留实际修复前状态，包括用户未提交修改；不能直接以 Git HEAD 代替。
- [ ] 用户明确选择并授权后只修复该问题，提供差异和撤销本次修改的步骤，保留无关改动。构建、测试或其他项目执行按已有执行边界进行。
- [ ] 修复不能靠删除需求功能、改写验收测试或替换成同类危险 API 达成。功能失败时说明结果并交给用户审查，不自动恢复漏洞代码或无限重试。

**完成标准：**至少一个首轮支持的修复在真实宿主完成，用户看懂改动并能审查。代码变化、任务换对象或范围扩大后，不沿用旧授权和旧证明。

**入口：**[任务修复](../src/security_runtime/task_fix.py)、[修复状态](../src/security_runtime/remediation.py)、[任务修复回归](../tests/test_task_fix.py)、[专项修复回归](../tests/test_dynamic_function_fix.py)、[修复复验验收](../scripts/fix_verify_acceptance.py)。

### 09 修复前后功能对照

**当前基础：**安全复验与功能验证已有独立结果。通用结果仍固定保留未知基线和未证明的回归归因；专项算术模板有前后模块哈希、正常值和 JSON 对照，但未验证真实 HTTP 路由。

- [ ] 首轮先接通一种技术栈和选定修复路径：编辑前保留正确源码版本及已有测试结果，编辑后运行同一组相关用例，并关联到同一修复任务。允许由宿主执行和记录，保留证据来源；不要求先建设任意项目的自动测试发现引擎。
- [ ] 输出分别显示原问题复查、修复前测试、修复后测试、编译或构建、未验证部分。区分原来就失败、修复后新增失败、没有基线、未执行和超时。
- [ ] 覆盖原有正常行为和相关边界。涉及接口时验证实际响应与错误处理；函数级模板通过不冒充接口通过。仅编译或类型检查通过，不显示功能未受影响。

**完成标准：**至少一个支持案例有可对照的前后结果和原问题复查；没有测试或可信基线时明确未验证。简单 tests_passed 标志不能自动升级为 Runtime 的安全关闭证明。

**入口：**[通用功能验证](../src/security_runtime/functional_verification.py)、[宿主执行契约](../src/security_runtime/functional_host.py)、[专项前后回归](../src/security_runtime/arithmetic_regression.py)、[功能回归](../tests/test_functional_verification.py)、[专项回归](../tests/test_arithmetic_regression.py)、[宿主验收](../scripts/functional_host_acceptance.py)。

### 10 日常触发正确和等待可接受

**当前基础：**内容比较、无变化跳过、工作区锁、并发事件保护和有上限的收尾检查已有。Git 副本模拟中批量 20 文件约 7.7 秒、连续 10 次修改约 76.3 秒；这些是特定旧构建的观察值。

- [ ] 在最终候选上记录单次、批量和连续修改的实际范围、执行次数、同步等待和收尾等待。只读、相同内容不重复扫描；无变化不重复询问。
- [ ] 验证四事件并发、扫描中再次编辑、超时、取消和重连；未检查的新改动保留待检，旧证明不覆盖新版本。长操作有实际阶段提示，取消后清理相关进程。
- [ ] 用至少两个首轮规模的 Git 项目完成真实开发任务，记录累计新增等待和用户是否中断检查。等待不可接受时先减少重复触发、复用有效结果和合并必要检查，不跳过检查来改善数字。

**完成标准：**上述行为正确，真实任务中等待经试用预演确认可接受。首次数据下载、准备完成后的编辑检查、整库检查分别测量；首轮不承诺通用秒级指标。

## P1 根据首轮反馈补齐

| 工作 | 首轮可用的最小替代 | 升级时机 |
| --- | --- | --- |
| 通用功能基线与测试自动发现 | 支持修复路径中的宿主前后记录，清楚标注范围 | 用户经常卡在选择或执行相关测试 |
| 稳定问题身份和到期例外 | 当前上下文的人工决定、可恢复暂缓和变化重审 | 行号变化重复提醒或跨扫描续办成为主要负担 |
| 后台漏洞数据更新 | 显示日期、过期提醒及手动刷新 | 持续启用后经常出现数据过期 |
| 进一步降低连续修改等待 | 保证触发正确，先做去重和有效结果复用 | 实测累计等待妨碍真实任务 |
| 更多依赖声明归属和传递引入来源 | 首轮生态的直接依赖与已证明的有限来源 | 大量任务因同一解析缺口无法处理 |
| Markdown 报告和稳定导出入口 | 当前聊天结果、本地历史和脱敏反馈 | 用户需要分享、留档或跨工具继续 |
| 更多框架及 Vue 等输入 | 披露未支持范围，首轮按已验证路径选项目 | 首批主要项目依赖该框架时，提升为 P0 范围内工作 |
| 凭据轮换待办的完整生命周期 | 提醒轮换或停用，人工记录状态 | 用户需要持续跟踪外部处理结果 |
| 公开安装渠道和更新服务 | 可信本地候选包与已有升级入口 | 从受邀试用转为公开招募 |

## P2 扩大用户范围后推进

| 工作 | 推迟原因 |
| --- | --- |
| 三栈全面质量承诺、更多编辑器和操作系统 | 先证明一个宿主和主要技术栈的完整体验 |
| 非 Git 项目的完整体验和性能 | 首批限定 Git 项目，保留现有能力的真实边界 |
| 完整跨文件跨库可达性、复杂攻击链和任意业务逻辑审计 | 首轮使用有限证据和选定问题核查，持续扩展 |
| 无人值守批量修复和自动合并 | 首轮保留用户选择、差异审查和验证 |
| 新增 CI 平台、SARIF、SBOM 和组织门禁 | 优先完成个人开发中的风险处理体验 |
| 企业权限、共享策略、审批审计与集中仪表盘 | 需要明确组织试点和新的服务能力 |
| 恶意包防火墙及 Agent 治理平台 | 与首轮要验证的风险决策和修复体验距离较远 |
| 大规模产品对照评测 | 先用独立小样例和真实任务查清失败；保留现有评测规划 |

已实现的能力可以继续使用；延期表示不为首轮增加新建设或扩大承诺。若某项直接阻塞选定试用项目，应缩小项目范围或把必要的局部工作提升为 P0。

## 实施顺序和通过条件

先完成 01 的支持范围和身份记录，并准备 11 的独立样例。02、03、04 构成可安装、可检查、状态一致的第一批；05、06、07 可以在范围明确后并行。08 的修复范围与前置状态确定后接通 09；10 贯穿所有实际任务。修改完成后重新冻结 01 的最终候选，对应完成 02、03 和 11 的验收。

邀请前必须有一条真实路径：新人安装，进入项目，实际编辑触发检查，理解一个候选，选择核查或处理，审查修改，看到原问题复查和功能结果，重开聊天后继续。安装或扫描失败、覆盖不足、未执行功能测试均有独立可见状态。

首轮试用的体验目标为：至少 4 人按说明完成接入和首次检查；至少 4 人无需逐条讲解就能解释优先问题及下一步；至少 3 人在第二次真实任务中主动使用。这些目标需要在预演后固定，有限样本不推导整体准确率或市场效果。

若出现真实风险被错误关闭、关键功能被修复破坏却报告通过、项目或授权串用，以及检查失败却报告安全，先修正并复验同一案例，再扩大试用。普通说明和等待问题按实际失败原因调整优先级。
