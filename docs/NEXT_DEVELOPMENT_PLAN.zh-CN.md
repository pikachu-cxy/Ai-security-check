## token 与时间监控实施计划

### 第一阶段：先让记录可信

复用现有 `context-usage status / compare / import-codex` 与本地统计库，先核对实际安装的构建身份和采集覆盖，不另起一套重复计数。当前能力与边界见[监测指南](guides/CONTEXT_COST_MONITORING.zh-CN.md)。

| 维度 | 已有基础 | 待补齐与验收要求 |
| --- | --- | --- |
| token | 显式导入 Codex CLI 用量，区分输入、缓存输入、输出与推理输出 | 标明宿主、模型、运行标识及用量来源；桌面端或其他宿主无可核对 usage 时显示未知，不自动搜索会话日志 |
| 响应量与重复 | MCP 文本、结构化及完整返回字节，源码交付行数、重复回执和复用标记 | 可定位返回量最大的调用和重复交付；字节数单独展示，不能称为实际 token 或费用 |
| 时间 | 每次 MCP 响应前耗时与按工具累计耗时 | 补充可关联的开始/结束及阶段记录，区分扫描、证据读取、复核交接、提交、重试、锁/队列等待；未观测部分显示未知 |
| 用户等待 | 现有 MCP 时长不覆盖完整会话 | 单独定义任务开始至结果可见的实际用时；模型处理、宿主调度、网络等待只有直接证据时才细分，不能由差值推定 |
| 数据质量 | 记录上限、保留期、签名核对及不完整计数 | 识别截断、缺失、重复、重连、重试和计时范围；记录构建、系统、宿主与采样条件，支持有界导出 |

输入与输出之和是总 token；缓存输入与推理输出分别是其子集，不再次相加。完整运行的真实 token 不能直接归到某个工具；无调用级用量证据时只并列展示。并发调用耗时之和不等于用户等待时间，阶段父子计时也不能重复累计。

采集只保存归因所需的有界元数据，不保存业务源码、提示词、参数正文、凭据或原始会话标识；沿用本地存储、不上传的边界。先明确保留期和导出方式，监控开销本身也需单独测量。

### 第二阶段：把消耗展示出来

首轮离线报告与独立本机实时页面已进入源码；实时页面每 2 秒刷新，提供采集开关、聊天/项目/手动窗口及扫描入口范围。完整产品任务身份、开发与扫描 token 拆分、内部阶段计时仍未实现。已有合成基准 HTML 仅用于字节对照，不能当作真实使用看板。页面启动与可移除契约见[实时页面指南](guides/LIVE_MONITORING.zh-CN.md)。

- 总览：真实 token、返回字节、调用次数、任务实际用时和累计工具耗时分别展示，缺失值不填零。
- 排名：按工具/阶段查看响应量、累计耗时、调用次数、失败与重试；展示单次最大值及 P50/P95，并显示样本量。
- 时间线：呈现阶段顺序、并发、重复读取和等待；可从高消耗项追到脱敏后的调用元数据。
- 筛选与快照：按运行、时间段、场景、构建和宿主筛选，支持导出用于后续比较；切换筛选后总览与明细一致。
- 数据质量：醒目标明实际 token 来源、观测范围、未覆盖阶段、过期/不完整记录和监控自身开销。

用已知输入的固定样本核对汇总、重复导入、并发时间及未知值，再用真实记录核对展示。可视化不能触发项目扫描、模型请求、安装或自动修复。

下一批优先补齐计量证据，不进行执行策略优化：

1. 将明确的产品操作身份与独立观察窗口关联，分别标明“聊天总量”“开发专属”“产品扫描专属”和未归属部分；没有证据的历史记录不反推。
2. 在可选观察接口中补齐扫描器执行、准备、复核和等待的起止，避免父子阶段与并发重复累计；监控接口缺失或失败仍须保持产品结果与体验。
3. 明确单次模型 usage 的宿主来源与活动关联；拿不到真实 usage 时继续显示未知，不按字节或工具调用次数估算。
4. 完成 Windows 本机页面与移除验收，再扩展固定场景采样。当前 macOS 72 项定向回归不替代跨平台或全库验收。

### 下一批任务边界与隔离验收

当前页面仍采用手动窗口，每 2 秒刷新不会创建、结束或重置任务。后续按“用户下达一个开发目标 → 完成该目标交付”建立观察身份；同一目标中的补充、修改和继续沿用身份，新独立目标再建立下一任务。任务监控身份应独立于产品安全任务账本，不直接把共享 MCP 连接或每条聊天消息当作产品任务。

验收需覆盖任务开始/结束、取消、重连、宿主延迟结算和并发活动；没有直接证据的用量保留未归属，历史数据不追补。先测量统计设置读取、数据准备、写库提交及页面轮询的完整开销，对照关闭采集、开启采集、停止页面与移除模块的行为；功能结果与性能开销分别报告。继续不实施性能优化，待真实归因报告后由用户决定。

### 第三阶段：先出消耗分析，再选择优化

在明确选定的任务中采样：普通聊天/只读、首次检查、无源码变化的重复检查、正常开发任务核查、中断恢复。每个场景记录样本量、模型/宿主版本、构建、规则、起始历史、检查范围与缓存条件；冷热启动分别观察。

先形成一份可追溯的消耗报告：哪些调用最多、哪些返回最大、哪些阶段最慢、哪些重复发生、哪些仍无法归因。当前已有的摘要、分页和结果复用机制作为基线保留，不预先承诺节省比例，也不为降低消耗缩减必要证据。完成监控、看板和真实采样后，由用户决定优化顺序。

## 桌面验收矩阵

1. 普通聊天、只读和无改动不启动检查、不追加旧缺口提示。
2. 普通开发只改授权文件；静态零发现仍按计划完成代码复核。
3. 关联已有风险保留防护与前提，默认提示包含位置及四段正文。
4. 只问影响时不编辑；明确同范围授权后不重复批准；测试依据与安全复查分别报告。
5. 原风险关联修复及复查，不能用另一个零风险任务代替关闭。
6. 原始候选、AI 有证据误报、用户排除/暂缓、跨聊天回读分别成立；恢复提醒不等于修复授权。
7. 引擎失败、存储异常、锁竞争、过期和重连保留真实状态，不能清空历史或扩大权限。

使用[当前手工验收](RUNTIME_CHAIN_REGRESSION_ACCEPTANCE.zh-CN.md)。故障注入由自动回归覆盖，桌面验收不手工破坏用户状态库或锁文件。
