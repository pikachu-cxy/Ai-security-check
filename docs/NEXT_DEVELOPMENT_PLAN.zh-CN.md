| agent 复核 | API 有分页，但计划和导航先整体生成后写入 task JSON；另有 10,000 units、100,000 reads、总 128 MB 交付预算 | [task_review/plan.py](../src/security_runtime/task_review/plan.py)、[task_review/budget.py](../src/security_runtime/task_review/budget.py) |

因此，只修改一个 `MAX_FILES` 会把故障推到正文存储、JSON 大小、扫描输入或复核预算上，并放大数据库锁与内存成本。

应保留的现有实现：正文已经按内容哈希共享；任务已有 owner、`routing_generation`、原引用标记与缺失历史保护；扫描已有固定输入、租约、取消和发布代次；队列已有后台自动重试。是在这些边界上扩展，不另外创建一套权限、扫描引擎或修复流程。最新工作区 `source_redaction.VERSION=3`，新存储必须保留每个原任务绑定的源码表示策略及旧版本读取，不能借容量改造切换原文/脱敏权限。

### 2. 先定义什么叫完整基线

#### 2.1 产品比较基线与任务修改前基线

接受“以产品确定的基线为准”的产品方向，不追溯用户首次接入瞬间。基线必须是可读取、不可变的版本记录，不能只确定文件路径后继续读取不断变化的活目录。以下为拟新增契约，不改变当前 v3 的任务修改前基线要求，也不升级旧任务的证明能力。

| 类型 | 起点与用途 | 不具备的证明 |
| --- | --- | --- |
| 产品比较基线 | 产品完成范围确认和内容封存后发布 `baseline_epoch`；用作此后项目版本比较的统一参照，可以晚于首次接入 | 不证明首次接入瞬间、某个任务开始状态或风险作者 |
| 任务修改前基线 | 在实际首次编辑前，按任务准入规则取得并绑定该任务真实起点 | 不能用较早产品基线或接入后快照替代缺失的任务前像 |

产品比较基线记录根目录身份、策略/表示版本、捕获起止时间、范围封口序号、逐文件内容对象、缺口、来源一致性及发布代次。`SEALED` 只表示已接纳条目及其缺口记录不可变；是否清单完整、正文完整、同一时点一致分别判断。逐文件观测组成的产品版本可以作为比较参照，但须标记 `OBSERVED_ONLY`，不能包装成共享目录某个瞬间的原子快照，也不能用它证明跨文件扫描已覆盖某个真实运行版本。

首次接入完成、基线可比较、扫描完成、任务核查完成是四个独立状态。首次接入可先完成连接与路由建立，既有会话可继续开发；尚无产品基线时显示准备中或具体缺口，不假定其他会话能够等待。已有任务继续保留原记录及历史缺口，不在编辑后重新建立其修改前基线。

#### 2.2 固定范围与持续变化的目录

取消“前 N 个文件就是全部”的截断，保留每批文件数、字节数、执行时间、总磁盘配额和管理员硬限制。资源不足要暂停或明确拒绝，不截取前缀冒充完整，也不无限重试。

产品基线分开固定**策略范围、已观测清单、已封存内容**：

1. 捕获开始固定项目根与纳入/排除策略；默认不递归跟随目录符号链接，不越出项目边界，目录身份去重避免循环。生成目录只有命中明确的忽略策略才能排除，不能为了完成率临时排除正在变化的源码。
2. 在持久化捕获代次中流式枚举、逐文件保存内容与哈希。为本次观察设定有限执行/重试预算与持久化序号；到达封口条件后关闭本代次成员集合，不因后续新增文件不断重开已封口页面。文件持续变化时有限重试，仍不可读或不稳定则保留具体缺口，不能把未知正文当空文件。
3. 有冻结来源或可证明完整的变更日志时，记录明确的清单边界及连续性。普通活目录枚举即使正常结束，也只代表该轮观察；尤其在遍历期间新增目录、移动路径、创建到已经遍历的目录时，不证明封口前所有文件都已纳入。无法证明完整枚举时，可以发布带缺口的观察基线，但必须保留“范围覆盖未证明”，不能称大项目完整基线完成。
4. 本代次未接纳的后续发现路径、封口后新增/编辑/删除进入后续变化代次；未能判断发生先后的路径标记“首次发现、先后未知”，不能直接认定封口后新增。通过后续盘点和可靠事件补充比较范围，不向已发布基线倒灌正文；无可靠事件时不能只依赖 watcher 或已知路径列表。
5. 产品基线发布后，比较的是已封存内容与另一个固定观察版本。新增文件需要比较版本的清单证据，删除需要确认路径确实不存在；不稳定、权限失败或事件断档保留未知。需要扩展策略范围、补齐覆盖或重新锚定时创建新 epoch 并明确比较起点，旧 epoch 和原绑定保持不变，不能靠反复换基线消除净变化或重置额度。
6. 产品比较基线的中断恢复只复用已提交对象和原序号。无冻结来源时允许后续时间的新观察继续完成同一候选，但必须记录观察间隔、来源变化和一致性降级；这不适用于任务修改前基线恢复。原冻结来源丢失或任务前像缺失，仍按原契约报告历史不可用，不从活目录拼接旧时点。

该方案避免追逐无限增长目录：有限工作量后发布可解释的比较参照，或暂停并说明原因；不承诺任意持续写入下都能取得完整、强一致的项目版本。策略范围内持续出现的新路径仍属后续检查义务，不能以“未进入首轮清单”为由永久排除。

#### 2.3 完整性与强一致能力

完整性分开记录，不能用一个 `READY=true` 混在一起：

| 维度 | 必须能够证明的内容 |
| --- | --- |
| 范围 | 根目录身份、纳入/排除策略及版本固定；目录清单已结束，没有待枚举目录或未说明的截断 |
| 哈希 | 每个纳入文件有该版本的内容身份；新增、删除、重命名都有明确记录 |
| 正文 | 复核和扫描所需原始内容或合规表示可读取、校验并被引用保留 |
| 一致性 | 明确是不可变来源、受控写入屏障，还是仅观测到稳定的活目录 |
| 可恢复性 | 原来源标识、对象引用、捕获游标及提交代次已持久化，掉电不会换成另一个版本 |

“完整”是对固定的项目纳入范围完整，不是读取磁盘上一切内容。已有忽略目录、`.env` 原文保留限制、链接/路径边界、编码支持继续按策略处理并显示原因。大文件不能仅为了凑完整率而静默排除；基线可采用流式分块保存与哈希，扫描器/复核不支持的部分另报覆盖不足。**完整基线与完整扫描是两个状态。**

必须解决当前整体时间点的问题：任务 `begin` 在工作区锁外逐文件读取，之后主要重验 owner/任务准入；稳定读取每一个文件，并不证明所有文件来自同一瞬间。SessionStart 两遍比较能发现变化，也不能证明外部进程从未交错写入。

- 强一致来源：可验证的原生只读文件系统快照，或能覆盖全部参与写入者的写入屏障。原生快照是待开发的平台适配能力，不能宣称 Codex/Cursor 现在已支持。
- 独立任务目录：可以把一个明确的种子版本复制到单独目录，验证该目录与版本一致，并在第一次编辑前让宿主实际切入；基线针对该独立目录的真实起点。不能声称这个种子必然是原共享目录某一瞬间的原子快照，也不能自动声称具备操作系统写沙箱。
- 共享活目录：产品内锁只协调受控操作；用户编辑器、Shell 子进程、外部生成器可能绕过。双遍哈希、mtime、watcher只作为检测/加速手段，标记 `OBSERVED_ONLY`；不满足强一致要求时返回明确的不支持/冲突状态，不能伪报严格一致。
- 任务修改前基线必须在首次修改前完成准入；产品比较基线允许晚于首次接入发布。后台预热或较早产品版本不能直接当新任务真实起点。若宿主不能等待或约束首次编辑，标明任务前像能力不足，仍可提供产品基线比较，不以 Hook 已配置冒充严格任务核查已经保证。

### 3. 存储模型：任务只持有版本引用

为新任务引入版本化快照存储契约（名称暂定 `workspace-snapshot-v2`），保留 v1 读取适配。建议以职责拆分，最终模块名在 L0 确认：

| 数据 | 建议字段/职责 |
| --- | --- |
| `snapshot_header` | `snapshot_ref`、工作区身份、source_ref、基线类型、baseline_epoch、策略/表示版本、捕获起止时间与观察间隔、范围封口序号、完整性/一致性、捕获代次、状态、统计与清单根摘要 |
| `snapshot_entries/pages` | `(snapshot_ref, normalized_path)` 索引；文件类型、长度、原文对象引用、表示对象引用、缺失/排除原因；分页摘要 |
| `content_objects` | 私有不可变内容对象，可按块存储；按内容去重，采用安全存储域内的索引；对象句柄不授予读取权限 |
| `capture_jobs/cursors` | 目录队列或 Git 流游标、已提交页、原冻结源、租约与 fence；捕获进度不放在聊天响应中 |
| `task_snapshot_bindings` | 原 task_ref、owner、任务修改前基线引用、可选产品比较epoch、结束版本引用；两类基线不混用，可共享字节，不能共享任务权限和证据 ID |
| `activity_events/paths` | 事件幂等键、工具调用起始路由、路径索引、最后序号、未知范围标记 |
| `scan_plan/partitions/receipts` | 固定目标/上下文集合的引用、扫描器语义、来源身份、每片状态及覆盖回执 |
| `review_units/windows/evidence` | 原复核版本、分页条目、证据签发与累计用量，避免重新写整条大 task JSON |

对象先写私有临时文件，完成哈希、路径/文件身份校验后原子封存；短事务提交一页清单和游标。读取、哈希和文件复制不能包在长 SQLite 写事务内。`SEALED` 只由最后的短事务发布，其根摘要包含固定策略、条目和子页摘要。任务、队列、缓存、复核只保存引用与计数。

保留当前私有目录 ACL、链接检查、签名/HMAC、路径规范化和工作区/owner 校验；Windows 大小写、大小写重命名、Unicode 与别名目录不能形成身份碰撞。不能把内容哈希当跨任务读取凭证。可写工作区和扫描器不能使用会污染内容库的可写硬链接；使用复制或具有真实写时复制语义的受控方式。

### 4. 捕获生命周期与中断恢复

建议状态流：`ALLOCATED → DISCOVERING → CAPTURING → VERIFYING → SEALED`。另有 `WAITING_CAPACITY`、`CAPTURE_CONFLICT`、`CANCELLED`、`HISTORY_UNAVAILABLE`。产品观察基线的封存、范围/正文覆盖与一致性分别记录（见2.1—2.2）；以下第1、4、5项针对严格任务修改前基线，不要求首次接入的所有活跃会话停写。这些是计划中的新状态，不是现有已发布接口。

1. 首次任务准入先持久化原 task/source/capture 绑定与防重复标记，再开始捕获。返回稳定任务引用和进度；旧宿主不得把 `PREPARING` 当允许编辑。
2. Git NUL 输出和普通目录枚举流式写入清单；内存中仅保留一批，不能先建立全项目列表再假装分页。循环目录、非法链接、权限错误仍明确处理。
3. 以每批文件数、字节数和时间片控制资源，例如初始调优值 256 文件/8 MB/200 ms，任一达到即保存游标并让出执行权。它们只是起始调优值，**不是项目完整性上限**；单文件操作不可中断时不能声称严格满足 200 ms。
4. 已封存任务恢复时，只读取原 baseline_ref。未封存捕获恢复时，只能续读同一有效冻结来源；不能把恢复时活目录的后半部分拼成旧任务开始版本。
5. 只有在“尚未开始任何任务编辑、仍处准入阶段且来源重新验证”的情况下，才能作废失败的捕获代次后重新准入；保留该过程和真实起点。若已经编辑或无法证明写入连续性，原任务保持历史不可用，不自动重建。
6. 不在源码读取期间持有全局数据库锁。确需写屏障时，作用域为该工作区/捕获 epoch，并给出等待状态、超时与取消；不能令无关项目或读取操作长期阻塞。

SessionStart 改为建立会话路由并预热版本目录，避免再创建独立的 1000 文件“大快照包”。产品比较基线按工作区和策略协调捕获，多个会话不各自重复冷捕获、不争抢目录独占权；任务自己的修改前版本绑定仍在实际首次编辑前完成。旧会话快照继续由兼容读取器解释，不重写它的历史含义。

### 5. 编辑期间和多会话隔离

编辑期间继续不扫描、不遍历全项目、不进行全项目哈希。路径索引按 `(task_ref, path)` 更新；同一文件或同一行修改多次，只累计活动序号，改前内容始终来自同一 baseline_ref。最终比较原开始版本与固定结束版本；改回原样可消除净变化，但不能用事件数量代替字节比较。

工作区可以关联多个任务，不将整个共享目录独占分配给某个会话。工作区身份、owner/任务身份、产品比较epoch、任务起点及结束版本分别绑定。产品基线捕获由现有调度器的单一有效发布者协调，短事务与租约/fence 防止多个会话发布竞争；它不是覆盖整个编辑期间的目录写锁。发布新epoch不自动切换已开始的比较或排队任务，首次接入时已经开发中的任务不得被追认为拥有该产品基线的历史前像。

- 编辑事件在工具开始时绑定 `owner + task_ref + routing_generation + invocation_id`；完成时使用这个原绑定。切换目标后的迟到事件不能落到新焦点任务。没有可靠起始绑定的宿主事件记为未归属，不猜归属。
- Shell 或路径信息不足时只记录“需完整核对”。可靠路径用于排序和加速；存在未知事件、watcher丢失/溢出、跨平台不支持或外部写入可能时，收尾必须执行可恢复的完整盘点/必要内容核验。
- A、B 只有在实际开始版本相同且通过独立授权检查后才可共享不可变对象；B 晚开始，必须绑定 B 当时的版本。不能按“同一个项目”共享任务基线语义。
- A→B→A 切换必须保留 A 的 baseline_ref 和已有分片进度。新目标是新任务；普通追问不自动新建任务。
- 收尾入队时冻结活动序号及未决工具调用水位；worker最多确认该冻结水位，入队后才到达的活动继续pending，不能采用执行时最新序号把后来编辑误算为已核对。工具开始归属与切焦点在同一事务中排序；完成事件只消费原START记录，缺少可靠宿主调用ID时保持未归属。
- 共享目录仍然只能保证“任务与证据不串用”，不能保证“各自扫描只看见各自写入”。严格代码归属需要独立任务工作区；宿主自动切换、绝对路径写入约束分别验收，不自动宣传完整沙箱。

相同文件被A、B交错修改时，产品可报告“当前观察版本相对产品epoch的变化”，但不能把整段净变化或风险自动归给收尾最晚的任务。会话事件来源、版本差异和风险存在性分别保存；无法确定作者时保持未知。独立目录只作为宿主明确支持并实际切入后的能力，不为首次接入偷偷搬迁现有会话，也不把创建目录等同于后续绝对路径写入已被约束。

其他关联缺口：`global_mcp` 的会话登记及 `codex_host_claims` 默认将同一会话固定到一个根；`tasks/ownership` 的签名会话引用绑定工作区，不能跨根重用。`codex_event_adapter` 遇到部分目录外文件路径会保留未知范围，不能因此自动关联到另一个 worktree。`task_workspaces` 已有副本准备及任务绑定，但未实现宿主自动切入、同会话跨根可信握手或操作系统写入隔离。Runtime 从原项目的 Python 环境启动，仅说明程序位置，不说明检查目标；`get_runtime_info` 返回版本和能力也不证明目录绑定成功。

#### 5.2 目录准入与显式绑定方案

L0 定义以下契约与失败行为，L2 实现目录准入/会话绑定，L3 实现调用起始绑定和迟到事件处理，L6 做真实宿主验收。不通过取消目录校验、信任调用者字符串或自动重绑旧任务绕过冲突。

1. **精确放行已验证项目根。** 保留 Codex 配置、凭据、Runtime 状态和证据目录的保护；仅为已验证的 worktree 项目根建立窄例外，不整体放开 `~/.codex` 或 `~/.codex/worktrees`。核对规范路径、无链接/跳转边界、目录身份、Git top-level、git-dir/common-dir 关系和可用的宿主受管工作树登记。合法 linked worktree 的 `.git` 文件可引用仓库元数据，但不得把元数据目录纳入项目扫描范围。仅有目录名称、`.git` 文件或相同远程地址不构成宿主授权；缺少可信宿主登记时定义独立的显式准入方式，不能以“查不到受管登记”自动放开。
2. **支持真实位置及拒绝伪装。** 分别覆盖默认位置、自定义 Codex 主目录、永久 worktree 和普通用户创建的 worktree；按项目准入处理，不能硬编码本次用户路径。配置/状态目录的禁止范围、大小写/别名、替换目录、伪造 Git 元数据、损坏或过期登记均需校验；有多个禁止规则时，窄例外不得覆盖凭据和 Runtime 私有状态保护。
3. **拆开身份与角色。** 显式保存聊天初始目录（宿主可提供时）、任务执行根、基线/结束版本根和原项目来源关系。工作区身份以独立 checkout 目录及其有效身份为准，Git common-dir/仓库身份只用于关联，不能将主目录和多个 worktree 合并成同一个工作区。产品基线按执行根隔离；可授权共享内容对象，不能共用任务绑定、风险处置或证据ID。
4. **首次绑定与跨根握手分开。** 新聊天直接在 worktree 启动时，根据可信宿主事件及准入结果建立该根的会话路由。已有聊天从A切到B必须走显式目标激活握手，核对宿主实际执行根和切换权限，发布新的绑定代次及目标范围凭据；不能仅凭一次 `workspace_path=B` 的参数修改绑定。没有宿主确认能力时返回不支持，保留旧记录，建议在B新建聊天。现有任务不搬迁、不把A凭据改签成旧任务可访问B；B上的后续编辑在有效绑定及新任务准入后开始，A任务仍沿A原引用恢复。
5. **调用、检查与版本绑定一致。** 工具开始时绑定会话/任务、执行根、绑定代次及 invocation；完成事件沿原绑定落账。显式 `workdir`、文件绝对路径或可观测目标与绑定根不同，则记录目标不匹配或范围未知，不能只扫A便声称覆盖B，也不能未经准入自动改扫B。跨多个根的操作须有各自授权与任务绑定，否则保留未覆盖范围；无法解析的 Shell 不靠猜测关联。收尾及队列消费原执行根与冻结版本，不随聊天当前焦点变更。
6. **恢复不猜测、不扩大权限。** 绑定代次、切换结果及原任务关系应有持久化和失效规则，拒绝旧代次重放。重连后须重新验证可信上下文及目录身份；不能用连接内“最后一个项目”、task_ref 文本或同仓库关系恢复未知绑定。迁移前后的任务、基线和累计账本独立保存，产品比较epoch也不替代任务绑定握手。

#### 5.3 会话绑定只读诊断接口方案

L0 增加独立的只读诊断契约（接口名暂定 `get_workspace_binding_status`，最终字段与访问方式在L0定稿），供用户在新工作树聊天中确认“编辑哪里、绑定哪里、检查哪里”。它应在全局路由层进行有界预检，不能先要求 `admit/bootstrap` 成功才能返回诊断，否则当前目录误拒绝仍只剩通用错误。

| 诊断内容 | 返回要求 |
| --- | --- |
| 当前查询上下文 | 请求路径、规范化候选根、已验证Git top-level及worktree关系；宿主实际聊天/执行目录有证据才返回，缺失标未知，不能把调用者自报路径当宿主确认 |
| 目录准入 | 允许/拒绝/无法确认、具体阶段及稳定原因码、命中策略类别；例如Codex主目录保护、worktree验证失败、会话根不匹配、引用失效，不把这些都折叠成通用拒绝 |
| 会话与任务绑定 | 当前调用者获准查看的已登记根、任务执行根、绑定代次、记录有效性/新鲜度、依据是实时宿主确认还是历史记录；无登记、不可验证和无权查看分别处理 |
| 比较及检查目标 | 已绑定任务的基线/结束版本工作区和排队目标是否一致；没有任务或无权读取时明确未知，不自动挑最近任务 |
| 安装与状态分离 | Runtime程序/构建位置、工作区准入、会话绑定、基线准备、扫描/复核完成分别返回；安装目录与目标不同本身不是错误，绑定正确也不等于检查完成 |

诊断只读：不注册工作区、不签发会话凭据、不创建密钥/数据库/目录、不建立或补建基线、不启动后台准备/扫描、不重绑或修改任务、不安装组件、不联网。只允许有界本地元数据读取，不能读取源代码或全树盘点来完成绑定诊断；现有读取助手如有惰性写入副作用须拆分。诊断入口仍核对当前连接/宿主身份及原引用的权限，不能以“只读”为由接受其他会话凭据或泄露其他会话路径/任务记录。

未准入路径可返回当前请求自身的有限策略诊断，不得暴露该根上其他用户/会话的登记是否存在。原始凭据、HMAC、密钥、源码与内部状态文件正文不得返回；无权访问时保持有限拒绝信息。宿主无法提供当前会话可信身份时，只能返回请求路径的预检结果，明确会话绑定未知，不将自身的路由猜测作为绑定成功证据。

成功判定须同时有合法目标准入、可信当前会话绑定和执行根一致的证据，并返回所核对代次/时间；对任务检查还需目标版本与原任务绑定一致。输入路径合法、MCP连接可用、版本正确、组件READY或历史登记存在，都不能单独判定当前绑定成功。新接口和跨根握手分别声明能力，旧宿主不支持时显式保留限制。

### 6. 收尾只固定一次版本，按扫描语义调度

收尾产生完整 end_ref，统一读取流同时生成内容哈希、扫描对象和任务所需证据表示，减少当前结束捕获、原文复制、open 校验的多轮全树读取。由基线/结束清单的索引做流式比较，生成变更集合；大清单不进入单条 JSON。

队列只消费 end_ref，不能在等待后读活目录替换原输入。任务排队后继续编辑应形成另一个结束版本/复核版本；已完成结果保留为历史，是否适用于当前代码另行标注。页/对象完整性仍校验，只减少重复验证范围，不能因性能去掉校验。

分片不能简单按每 1000 个文件切断：

| 扫描类型 | 调度要求 |
| --- | --- |
| 文件局部规则、密钥检查 | 按字节/预估耗时分片，保留相对路径与配置作用域 |
| 跨文件/模块分析 | 使用明确上下文规划器，按模块或依赖闭包；闭包交叠时合并或完整提供上下文 |
| 依赖检查 | manifest、lockfile、父级/工作区配置作为依赖单元，一单元一次；原有不完整依赖图限制继续保留 |
| 全项目规则 | 对同一冻结版本执行项目级作业；不能安全分片的规则保持整项作业，容量不足时等待/标记缺口 |
| 未声明分片能力的引擎 | 默认不认为可任意分片；通过 adapter 的 `partition_contract` 明确支持范围 |

沿用现有 dispatcher、机器级资源名额和 queue 的 lease/generation fence，扩展作业类型和分片索引，不再创建一套与它竞争的独立调度服务。基线 I/O、引擎 CPU/内存分别限额；总并发必须考虑现有引擎内部线程，防止“会话数×分片数×引擎数”失控。任务间公平轮转，兼顾小任务延迟与大任务不饥饿。

完成条件是：计划已封口、全部必需分片都有有效回执、目标及上下文覆盖可解释。队列暂空、一个分片成功、当前零告警都不等于任务检查完成。失败只重试同一冻结版本的失败分片，已提交成功分片不重复扫描；旧 worker 失去租约后不得发布。

超过 128 个改前风险目标时，生成可恢复比较计划，而不是全体变成不可比较。逐条风险保留 `PENDING_COMPARISON`；完成前归属保持未知，不能因改前分片没执行就判断新增。当前没有风险继续不做改前补扫。风险的存在、影响和会话作者依然是不同维度。

缓存改为按输入/上下文/配置/规则/引擎/数据身份索引的分片事实，加入分片语义与闭包摘要；整项目结果只持有分片根引用。复用不共享 agent 结论、处置或证据 ID。跨分片去重保留各来源和不同暴露面，覆盖不足不能通过合并变成 FULL。

### 7. 复核、资源预算和垃圾回收

agent 接口保持有界源码窗口、签名游标、原复核版本和累计账本；从存储层分页产生单位/窗口，不先生成所有导航数组。读取和提交只更新对应条目，恢复时不重新签发已读覆盖或清空用量。

项目文件总数、变更文件数、复核源码总量分别计数。10万文件、修改1个文件，不应因项目总数耗尽整个 agent 复核预算；大规模真正改动仍需要相应审阅成本。对原 10,000 units/100,000 reads 等全任务保护，改为可持久化分段计划与明确的容量准入，保留全任务累计审计及管理员硬资源约束；遇到实际额度不足返回等待/部分完成，不建新 task 或新基线规避额度。

磁盘、内存、并发、单次响应和目录安全边界继续保留。区别是容量不足会暂停新准入/原作业并给出所需资源，不会只处理前 N 个文件后宣称完整。状态、进度和缺口列表也分页，指标用累计计数加有限样本，不受现有 10,000 文件/64 MB 观测截断影响。

GC 以引用及状态为主：task→baseline、queue→end、scan→input、review→evidence。活动作业不因后台 TTL 到期被直接删源；生命周期到期先明确转为 EXPIRED/取消并释放引用，再按保留策略回收。磁盘不足不驱逐活动基线腾位置。对象写完但引用未提交的孤儿有独立宽限期；带存储代次防止 GC 与新引用竞争。缺失/损坏原对象保持原任务缺口，不能回读活目录重建。

旧任务默认走原合同。完整且可验证的旧内容可转为只读分页投影，但保留原时间、摘要、owner、表示版本和限制；旧任务漏掉的第1001个文件不能从当前树补成原始基线。新旧任务可并存；回滚代码前先核对存储读写能力，旧构建应明确拒绝新契约，而非破坏新状态。

| 文件数量与资源预算 | 1001/10000/100000文件无固定前缀截断；每批可暂停续做。磁盘/管理员配额不足时保留计数、游标和原因；达到尝试预算明确退出或等待，不无限重试、不绕过配额 |
| 目录循环和越界 | 链接环、别名目录、项目外链接、权限拒绝和生成目录按固定策略处理；不能无限遍历，也不能动态排除源码冒充完整 |
| 同项目并发发布 | 多会话同时请求产品基线时按工作区/策略协调复用同一捕获代次；失效发布者不能seal，权限不足不能读取共享内容；短锁不长期阻塞其他项目 |
| A/B交错编辑与迟到事件 | 同文件交错写入、A→B→A切换、工具开始后切焦点；事件沿原invocation路由，未知保持未归属。产品差异不作为任务作者证据，任务证据ID和处置不串用 |
| 发布后新增及重新锚定 | 新文件可在后续比较中发现和检查；新epoch发布不修改旧基线、不切换原队列输入、不清除旧差异或风险。策略改变有新身份，原任务账本和累计额度不重置 |
| 捕获与恢复中断 | 已提交对象保持不变；观察模式恢复保留间隔和未知覆盖，冻结模式只续原来源。对象丢失不从活目录补造旧正文，旧v3缺失任务不借产品epoch追认完成 |
| 宿主能力不足 | 无文件系统快照、写屏障、可靠起始事件或自动切目录能力时逐项声明；共享观察比较仍可用但不宣称严格任务前像/作者隔离。创建副本不算宿主已经切入 |

L0 必须明确两种不同的成功条件：**产品比较能力**允许晚于接入的可解释观察起点；**完整强一致任务核查**仍要求其独立的来源、准入与覆盖证明。不能为避免首次接入等待而降低后者的完成判定，也不能因后者暂不支持而阻止前者交付。

### 9. 功能、故障和性能验证矩阵

| 维度 | 场景 | 断言 |
| --- | --- | --- |
| 规模 | 1001、10,000、100,000 文件；500,000 文件可作扩展压测；分别改1/100/5000文件 | 清单计数准确，无固定前缀丢弃；未知项逐项可查；扫描/复核覆盖与实际范围一致 |
| 文件形态 | 大于256KB路径名总量、超过20MB源码、深目录、很多小文件、超大单文件、非Git、符号链接/大小写重命名 | 流式处理；不支持原因明确；不存在静默排除后冒充完整 |
| 并发 | 2/3/4个会话；相同/不同结束版本；同路径不同内容；目标A→B→A；迟到完成事件 | 共享内容不共享权限；基线和路由正确；共享目录不伪造作者；隔离目录互不污染 |
| worktree准入与路由 | Codex默认/自定义主目录内工作树、主项目与多个linked worktree、同聊天切根、绝对路径跨根 | 合法项目窄放行，内部状态仍保护；仓库相同不合并工作区；操作根/绑定根/检查目标有证据对应，未知不猜 |
| 绑定只读诊断 | 正常/拒绝/无登记/过期/无权查询，宿主身份缺失，Runtime程序位于另一目录 | 给出有权限的具体阶段和证据；零状态副作用；未知不等于成功；不泄露其他会话绑定 |
| 首次接入 | 多个既有会话持续增改；接入后才发布产品基线；无可靠起始事件 | 接入与基线/扫描/任务核查独立；不阻塞全部会话，不补认旧任务前像；记录产品起点及未知归属 |
| 范围封口 | 已遍历目录新增文件、目录移动、持续生成、发布后首次发现路径 | 有限尝试、不追赶无限增长；未接纳项转后续义务；范围覆盖未知不变完整；封口后不倒灌基线 |
| epoch比较 | 捕获期间修改已纳入、发布后新增/删除、重新锚定、旧任务仍排队 | 比较固定对象；不回溯首次接入；旧绑定/队列不被切换；风险和用量不因换epoch清空 |
| 一致性 | 捕获时替换文件、交错修改两个文件、外部编辑器、后台Shell子进程、watcher断档 | 检测冲突/降级或拒绝严格承诺；不能把双遍一致当OS快照证明 |
| 恢复 | 枚举、写对象、提交页、seal、排队、扫描、写回执、agent阅读/提交各阶段强杀 | 原task/source/baseline不变；未提交步骤可幂等重做；已完成分片不重跑；缺历史不补建 |
| 存储故障 | 磁盘满、对象损坏、权限变化、GC与续租竞争、进程失联、超期 | 可解释等待/过期/缺口；不丢活动引用；不把损坏对象当空文件 |
| 兼容 | 旧完整/旧部分快照、新旧混用、旧格式恢复、v3证据原文策略及旧表示、构建降级 | 旧缺失不补齐；旧任务不重新基线；不跨任务签发证据；不破坏已有数据 |
| 扫描语义 | 同一小型仓库整体执行和分片执行；跨目录source/sink；多manifest/锁文件；配置作用域；129+风险文件 | 发现和覆盖等价；保留原提供方限制；改前未扫描不等于无风险 |

性能按 `discover/read/hash/object_write/materialize/queue_wait/engine/merge/before_compare/agent_delivery` 分阶段采集。记录冷启动与热启动的 P50/P95、首个结果与最终结果耗时、峰值RSS、每批数据库锁时间、读取/哈希字节与次数、缓存命中、GC空间及队列公平性。记录硬件、文件数/字节量、构建、策略和命中率，不用小样本单次耗时代表大项目。

先确立算法门槛：

- 编辑 Hook 工作量随本次事件路径数增长，不随整个项目文件数增长；不逐次全树遍历。
- 单次内存与数据库写入随批大小增长；根目录枚举、diff、缓存查找和复核导航不把全项目状态载入一个对象。
- 有可信不可变版本/变更连续性时，热路径只读取变更及必要上下文；没有可信连续性时允许完整盘点/哈希，明确其成本，不偷换成mtime安全证明。
- 冷基线允许总成本随文件/字节数线性增长，但支持进度、取消、公平调度和原来源恢复。具体秒数与资源默认值由 L6 基准决定，不能提前承诺。

建议新增专门测试组 `tests/snapshots/` 和规模夹具，名称在 L0 固化。现有 `tests/tasks/test_task_snapshot.py`、`test_task_preimages.py`、`test_task_preimage_sharing.py`、`test_task_ownership.py`、`test_closeout_lifecycle.py`、`test_closeout_queue.py`、`test_task_workspaces.py`、`test_unified_scan_lifecycle.py`，以及 `tests/test_scan_input.py`、`test_scan_reuse.py` 和 `tests/task_review/` 可作为回归基础。大规模测试使用仓库外临时目录，避免测试产物进入项目盘点；真实登录恢复、文件系统快照和跨宿主桌面能力需独立验收，不能以单元夹具代替。

### 10. 完成的定义

只有 L0—L6 所需产品路径均闭环，规模与故障矩阵（含首次接入、持续编辑和产品epoch比较）通过、原有覆盖语义不下降，且当前宿主实际接入已验证，才称“大项目改造完成”。产品观察比较可按自身验收单独交付，但不得等同于完整强一致任务核查。若只能完成分页存储而宿主不能保证写入屏障，或扫描分片尚未覆盖项目级规则，应逐项标记部分完成。

本计划不包含自动最终报告送达确认、操作系统全写沙箱、自动合并/归档等已有宿主缺口的默认实现；这些能力与本方案相交时只报告真实支持程度。不得用它们的未实现状态取消已授权的存储/队列开发，也不得反过来宣称严格隔离已经具备。
