## 本次方案调整

原有产品边界和三类修复通道继续保留，本次按更新源码调整以下实施要求：

- 接入已存在的 `security-reply-plan-v1`，修复影响与漏洞后果分开，不另建提示、选择和授权状态。

- 增加业务文档类型、脱敏截断、领域错误、旧修订风险及部分结果持久化的验收。
- 根据 A/B/C 补齐严格嵌套字段、合法枚举和修正提示；增加原生风险 `prepare_task_risk_fix／cancel_task_risk_fix`，以及已登记选定修复意图对同 owner 普通 begin 的守卫，保留原授权与基线。

## 分批实施

各批按依赖顺序交付，不以固定日期或预估测试数量代替通过条件。每批只运行与实际改动相关的内部研发检查；以下检查是本产品研发验收，不是个人版面向用户新增功能测试能力。

| 批次 | 工作与主要接入点 | 必须交付的结果 | 进入下一批的条件 |
| --- | --- | --- | --- |
| 0 | 当前交互验收与接入盘点 | 记录实际通过候选；对照相关源码摘要，盘点分组与原生风险、修订、共同回复、票据和宿主通道 | 本轮明确开工授权已记录；当前相关修复与候选关系明确，引用、授权和续办规则已对齐 |
| 1 | 数据契约与私有存储 | 两类来源 union、原响应选择及活动成员、原风险版本与分析版本、评估 owner、状态、有限账本及兼容迁移 | 跨工作区和越权写入拒绝；历史只读不转移 owner；旧风险、决定和授权不覆盖；旧修订无法解析时不换用最新风险 |
| 2 | 独立上下文与义务计划 | prepare/read/submit/get 服务；安全读取与引用适配、必要文档类型、版本窗口、分类容量与分批、部分结果保存 | 不调用任务 prepare／finish／扫描；全部已识别必读义务入计划，遮盖和截断保留未知；重复请求不重置消费，容量耗尽不丢结果 |
| 3 | 批准分支门槛与现有修复链 | approve=True 的 grant／票据前核对；原生 prepare／cancel、意图守卫及修复基线；保留原授权、成员范围和 envelope | 仅查询不编辑；拒修／处置不要求先评估；原生 ts1 不进 scanner 入口；提交失败不以裸 begin 绕过；已有授权不二次追问，过期和超范围不能放行 |
| 4 | 共同回复投影与错误契约 | 影响事实接入共同回复；严格嵌套 schema、合法枚举和有界字段错误；本地／全局路由与安装 Skill 同步 | 两类影响可区分，已授权／抑制／处置未知／过期项不重建选择；参数和归属错误不误报连接失败，不要求重装，不出现功能测试推荐 |
| 5 | 候选与真实宿主验收 | 固定源码/包/规则/Skill 身份，按下述矩阵走真实 Codex 路径并登记耗时 | 内部检查、候选构建和真实桌面结果分开留证；用户确认本功能验收后才扩大宿主支持及交付范围 |

批次 1 的数据校验与批次 2 的样例规格可并行；批次 3 依赖两者。第一批不同时扩大多宿主、自动修复规则和深度验证能力。Cursor 的只读工具、可见反馈、编辑约束及续执行分别验收，其他宿主不沿用 Codex 结果。

## 接入盘点交付物

批次 0 需要一张以源码和实际宿主证据为依据的支持表，至少列出：

- `TaskFixService.prepare` 的扫描器分组解析、活动成员过滤、处置变化和原组逐成员复查；不假定已有任意组内子集参数。
- `RemediationService.confirm` 的 approve=True／False 分支、`prepare`、inline ticket 和精确 envelope 的签发、消费与保鲜位置；`generate_fix` 只生成建议，不作为编辑关卡。
- 开发任务原生风险的原修订、快照、归档详情、处置和代码复核路径；确认不混用扫描器任务引用，也不以最新风险替代旧风险。
- 通用宿主编辑能否可靠拦截；只有指导约束的路径必须明确标注。
- 独立影响服务可复用的安全读取／预算纯逻辑与原任务编排副作用；显式列出业务文档和原扫描清单外文件的支持边界。
- MCP、Hook、安装 Skill 和各宿主对共同 reply_plan、领域错误及交互契约的消费位置。

现有快速票据限制读取和搜索，不在票据发出后追加跨模块分析。新增分析支路先结束，再让原修复链处理当前有效授权。不能因为新增影响评估，就默认启用任意规则自动修复。

## 验收矩阵

每个案例预先固定问题来源、合法业务规则、危险路径、用户表达、预期编辑范围和判定依据。涉及两类问题来源的案例分别执行，不能用其中一种通过代表全部通过。

| 案例 | 必须观察到的结果 |
| --- | --- |
| 单条已选告警后说“修复” | 评估发生在编辑前；沿用原具体授权，不重复询问同一批准 |
| 多条告警只说“修复”且目标不明 | 只澄清目标，不全组编辑 |
| 明确选择第 1、3 项，之后摘要重排 | 仍绑定原响应的两项准确引用和活动成员；不按新排序换对象，授权、影响和复查逐项可追踪 |
| 用户仅选择扫描器分组内一条告警 | 不扩大为全组授权；不假称现有 prepare 支持任意子集，范围无法表达时明确不支持或使用既有准确定向路径 |
| 分组包含暂缓／排除项或评估中处置变化 | 仅处理有效活动成员；成员变化使旧范围待刷新，不恢复已抑制项，也不偷偷替换成员 |
| 没有既有修复授权时只问“会对功能产生什么影响” | 返回具体分析；无源文件变化、无修复确认、无新扫描或开发基线 |
| 已授权修复过程中追问影响 | 先回答影响，再按原有效范围续办；明确暂停或出现新业务取舍时才停止相应编辑，不把追问当撤销授权 |
| 查询后再明确修复 | 可复用当前有效材料；不把先前查询计为授权 |
| 原生风险影响提交未被接受 | 用户明确修复后取得原评估引用即尽早调用原生准备登记 WAITING，再完成 read／submit 并重试；明确未保存及具体修正字段，不把 DRAFT／已读完当 READY，不重复同一授权；已登记意图阻止同 owner 普通 begin 替代 |
| 原生风险影响通过后准备修复 | 使用原 task／finding／impact 和 user_requested=true；直接取得独立 repair_task_ref 做 finish／review，原风险 resolution 与账本另行核对，不调用 scanner prepare_task_fix 或伪造 scan_id |
| 已登记原生修复后明确暂停或切换开发 | cancel 仅解除同一意图阻塞，原风险、处置、审计和基线保留；DEFER／EXCLUDE 保存成功自动解除，无须补影响或再次批准 |
| 同源重试或取消后恢复 | 不替换原基线；当前处置、方案、期限或关联依据失效时返回原修复任务待复核、ready=false，不能继续旧方案编辑 |
| 越权修复与项目共享成员耦合 | 识别共享成员正常访问，优先给出保留该行为的修复；不能直接限定只有创建者 |
| 业务规则确实需要改变 | 明确角色、操作、变化和替代方案；取得对应选择前不实施该变化 |
| 纯局部修复 | 简洁说明已查范围后继续，不机械增加确认或全仓阅读 |
| 共享组件有多个调用方 | 沿实际引用扩读并记录已查调用；搜索零命中不能证明无消费者 |
| 依赖升级改变已用 API 或锁文件 | 记录升级范围与具体未知，不声称完整依赖图或联合兼容验证通过 |
| 动态调用、外部客户端或跨仓未知 | 保留未知；关键业务规则不足时不实施该方案，不宣称全项目兼容 |
| 引用与正文不一致或证据被伪造 | 拒绝提交，保留可诊断原因；不生成通过门槛 |
| 同一 task_ref 推进复核修订后处理旧风险 | 原风险修订／快照与当前源码分别绑定；无法取回旧详情则说明缺口，不换用最新 finding 或 review_session |
| 同工作区查看另一会话已保存报告 | 按历史只读契约返回，不转移 owner、登记新取证、刷新预算或恢复授权；续办与提交仍检查当前评估归属 |
| 相关鉴权或配置被另一会话修改 | 编辑前发现失效并重评，不沿用旧结论或旧执行票据 |
| 只有注释、行号或无关内容变化 | 不撤销用户处置、不恢复已排除提醒；必要的证据刷新不变成重复授权 |
| 新方案超出既有语义或精确编辑范围 | 重新评估并按现有范围规则取得对应决定，不扩大 envelope |
| 既有授权过期或撤销 | 影响评估不能补发授权；原授权服务仍拒绝执行 |
| 重复请求、重连、锁忙、预算耗尽 | 原引用续办，消费累计；不重建基线、不靠新建任务清零 |
| 已识别必读范围超过旧 12／24 文件或小字节值 | 相关义务仍全部入计划，按硬容量预检与分批交付；不能因先读页无异常就宣称完成 |
| 多页、多离散窗口和后续关联义务 | 导航与源码、控制分别记账；只承认实际交付，漏读／漏提交不算完成，扩展失败保留旧进度 |
| 额度或活动租约耗尽后保存部分分析 | 可受控保存 PARTIAL 和停止原因、返回有界回执；回执不是通过，历史分页不重新分配取证额度 |
| 活动续租、真实新修订、证据到期 | 续租不增额度或延长材料／grant；新修订保留历史消费，材料已失效时不承诺无条件续办 |
| 需要业务 Markdown 或原扫描计划之外的关联文件 | 仅通过新增适配器允许的类型与来源读取；旧任务接口不支持时不冒充已读取，不绕过路径或脱敏保护 |
| 关键角色／条件被遮盖或长行截断 | 保留具体未知，不能根据掩码推断业务规则、不能放宽脱敏来取得通过 |
| 用户拒绝修复或选择 DEFER／EXCLUDE／RESTORE | 无须先取得影响 READY，仍按原处置流程保存；不消费新的修复尝试 |
| 生成修复建议后再分析影响 | 可先得到 coding task，仍无编辑授权；无“先评估才能出方案”的循环 |
| 参数、owner、revision、预算或存储错误 | 本地和全局返回一致领域原因，不误判项目未导入／连接配置失败，不回显任意异常内容 |
| 旧客户端、旧记录、进行中票据升级 | 历史记录保留；缺影响信息不冒充评估完成；不改变进行中票据范围 |
| 已启用门槛的连接自报旧版本或请求降级 | 不能旁路新 grant 的影响校验；缺能力明确返回不支持，产品入口由可信构造器接线，客户端没有降级开关 |
| 用户暂缓、排除、恢复提醒 | 沿用新版人工处置语义；影响分析不改写风险结论或擅自恢复提醒 |
| 修复后原问题安全复查通过 | 只证明相应安全范围；影响说明不变成整个项目功能正常的承诺 |
| 分组只有部分成员修复 | 保留逐项结果及 PARTIALLY_RESOLVED；评估完成不能冒充整组关闭 |
| Hook、总结和主动查询同一问题 | 状态一致，同一修订不重复长提示；实际业务变化仍可清楚查看 |
| 漏洞后果与修复影响同时展示 | 漏洞 RiskFact.impact 不被覆盖，新增影响事实经同一回复计划投影，事实仍不授予权限 |
| 已授权、已抑制、处置不可读或适用性未知 | 沿用 reply_plan 过滤，不重建 FIX／DEFER、不回退旧提示；影响状态改变不重置原授权 |
| 存储或读取失败 | 不声称保存成功、不误报连接故障；未保存记录与原风险状态分别说明 |
| 个人版默认能力与回复 | 无功能测试工具、推荐或“功能未测导致安全检查不足”的提示 |
| 交互候选内部检查完成、桌面仍为 PENDING_USER | 保留真实待验收状态；本轮明确授权可以开工，但不把内部检查数或开发批准当用户桌面验收 |

内部研发检查优先覆盖状态转换、来源修订与活动成员、历史访问／归属隔离、过期与并发、批准／拒修分支、义务覆盖与分类预算、部分结果持久化、隐私脱敏和领域错误。按实际改动扩展现有 `test_reply_plan`、`test_risk_decision_experience`、`test_task_fix`、`test_remediation`、`test_task_review_revisions`、`test_local_evidence` 及票据／隐藏入口相关回归；通过后再进行真实桌面验收，不用内部检查替代用户交互表现。研发检查和构建的实际执行、结果及缺口以独立运行回执为准；不得据此段计划文字推定已执行、已通过或尚未执行。真实桌面验收继续保持 `PENDING_USER`，逐项结果须由真实案例确认。

## 完成标准与交付证据

本轮真实 A/B/C 结果见[验收记录](REPAIR_IMPACT_ACCEPTANCE.zh-CN.md)：A 在影响提交被拒绝后仍编辑；B 解释正确但分析未保存、授权修复阻塞；C 暂缓持久化成功但正式影响历史为空。三项均不能登记整体验收通过。针对这些缺口的工作树修正已进入回归与候选验证流程；真实失败与后续结果按本轮回执保留，真实桌面复验保持 `PENDING_USER`。此前内部回归、旧候选与冻结探针结果只属于当时版本，不能转用于本轮源码；只有对应层次的成功证据才能更新 latest 或验收矩阵。

完成时应同时具备：

1. 对新增模块和所有可达入口的准确能力表，区分 Runtime 可校验门槛与宿主指导约束。
2. 带原风险修订与当前来源的影响记录，以及覆盖全部已识别必读义务的计划；区分危险行为限制、正常业务变化和未知，无全局兼容性通过状态。
3. 用户问题、业务选择、编辑授权、风险处置和原问题安全证明分别可追踪。
4. 上述关键矩阵通过，当前风险处置与共同回复桌面场景没有回退，累计等待、重复阅读、分类消费和容量不足保存有实际记录。
5. 以同候选记录内部检查、构建、安装与真实宿主验收；未支持的宿主或通道明确保留边界。
6. 更新实际能力说明、构建与内部检查回执；用户完成并确认桌面案例后才登记验收通过，扩大支持范围须有对应证据。

首轮不以样例数量推导准确率。先记录目标方案是否误伤正常路径、是否遗漏明确共享调用、是否多问一次批准，以及一次修复实际增加的等待。资源硬边界以 0.3.6 的 `repair_impact_models.py` 为准；义务分配与实际分类消费以实际执行的定向内部回归及其记录为准，候选回执只关联确已完成的检查及结果。新版冻结探针验证启动、构建身份、契约、六工具及嵌套 schema，不代表冻结进程已经运行影响分析、产生过分类消费或执行原生准备／基线守卫。桌面体验阈值按真实预演记录核对，不以文档预估取代实际结果。

## 接续与回退

接续时先读取本轮候选及内部检查回执，再读取本计划和架构设计；沿当前明确授权及原任务推进，不另建基线或要求重复开工批准。旧交互候选的桌面待验收状态仍保留，新候选逐项完成实际验收后再登记结果。

0.3.6 由可信产品 MCP 构造器默认接线影响服务及编辑前门槛，包括全局工作区子连接的产品修复工厂；客户端没有环境变量、版本自报或 MCP 参数开关。直接嵌入 `RemediationService` 且未配置 `impact_gate` 时保持旧调用兼容，不宣称具备强制门槛。实际模块为 `repair_impact.py`、`repair_impact_models.py`、`repair_impact_context.py`、`repair_impact_store.py`、`repair_impact_sources.py`、`repair_impact_contract.py`，门槛计算位于服务 `_gate` 及模型校验。

旧候选缺少本功能时按其原契约处理；回退不得清空用户的暂缓、排除、恢复和评估记录，也不得将评估缺失写成通过。当前候选的桌面验收保持 `PENDING_USER`；只有真实用户案例确认才能更新验收结果，能力已接线不等于桌面已验收。
